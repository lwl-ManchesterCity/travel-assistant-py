## 1. 目标与非目标

目标：用户一句"第二天太赶，砍掉一个景点"，系统**判断出这是修改意图**，把它归一化成一句
`/api/trips/adjust` 能吃的 `adjustmentPrompt`，**经用户确认后**走已有的改方案链路，
新方案回到页面上，还能继续追问。

非目标：

- 不让 agent 自己改方案：agent 全程只读、只产文本，写动作仍由 `/adjust` 做。
- 不重复实现一套"自然语言→请求字段"的解析器：那是 `TripAdjustmentAgent` 已有的活（LLM 路径 + 规则兜底两条）。
- 不做撤销/回滚、不做批量多轮改、不做会话记忆（会话是 C 档）。
- 不改 `/api/trips/adjust` 的入参、响应体、错误分支——它的契约保持不动。

## 3. 关键设计：两段式 + 人在中间

```
用户："第二天太赶，砍掉一个景点"
  ↓
POST /api/trips/ask           （只读，不改任何东西）
  返回 intent=need_change
       answer="我打算这样改：第2天只保留主景点、压缩通勤"
       adjustmentPrompt="第二天行程太赶，节奏轻松一点"
  ↓
前端弹确认层（复用 .trip-adjust-overlay 的样式）
  [ 确认修改 ]  [ 算了 ]
  ↓ 确认
POST /api/trips/adjust        （已有端点，一字未改）
  originalRequest = 前端手上的 request
  adjustmentPrompt = agent 归一化出来的那句
  ↓
新 TripPlan → 覆盖 currentTripData / currentPayload → 可继续追问
```

为什么不让后端一步到位直接改：

1. 一次改方案 = 一次完整重规划，40~70 秒、还会占高德每秒配额。意图误判的代价是**一整次重规划**，
   而确认这一步把它降到一次点击。
2. agent 保持零写权限，"事实由确定性链路产出"这条边界不破——面试时这一条能顶很多问。
3. 确认层本身就是 08 章 human-in-the-loop 的落地，比"全自动"更能说明你懂控制点在哪。

## 4. 契约变更

`AskResponse` 加一个字段，其余不动：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `answer` | string | `need_change` 时是"我打算这样改…"的人话 |
| `intent` | string | `answer` / `need_change` |
| `adjustment_prompt` | string? | 仅 `need_change` 时有值，是给 `/adjust` 的那句话 |
| `traces` | AgentTrace[] | 不变 |

模型最后一轮必须输出固定 JSON 二选一：

```json
{"intent":"answer","answer":"…"}
{"intent":"need_change","answer":"…","adjustmentPrompt":"预算改成2000，住经济型酒店"}
```

解析失败（不是合法 JSON、缺字段、intent 值不合法）时**一律回落 `intent=answer`**，
把模型原文当 `answer`，并记一条 `status=fallback` 的留痕。理由：误判成"要改"会白烧一次重规划，
误判成"只是问"用户再点一次编辑行程就行，两边代价不对称。

## 6. 验收判据

单测（新增 5 条）：

1. 模型输出 `need_change` JSON → `intent=need_change`、`adjustment_prompt` 有值、`answer` 有值。
2. 模型输出非法 JSON → 回落 `intent=answer`，且多出一条 `status=fallback` 的留痕。
3. 模型输出 `intent` 为未知值（如 `modify`）→ 同样回落 `answer`。
4. `need_change` 时**没有产生任何写副作用**：断言 `/adjust` 的 service 没被调用（用 stub 计数）。
5. 归一化出的 `adjustmentPrompt` 能被 `TripAdjustmentAgent` 的规则路径识别：
   拿"预算改成2000，住经济型酒店"喂规则解析，断言 `appliedChanges` 至少两句。

真实跑（双向各 10 条）：

- 该改的判成 need_change ≥ 8/10：`预算改成2000`、`第二天太赶砍一个景点`、`换成经济型酒店`、
  `不要美食多一点自然风景`、`节奏轻松一点`、`加一天`、`住得离西湖近一点`、
  `别安排这么多博物馆`、`晚上想吃点好的`、`把第三天删了`。
- 不该改的误判 ≤ 1/10：A 的那 10 题里挑 8 题 + `把第二天改松一点怎么办比较好`（咨询口吻，答"可以砍一个点"）
  + `如果下雨怎么办`（问的是应对，不是要改方案）。
- 闭环一条：确认"预算改成2000"之后，新方案 `budget.requestedBudget=2000`，
  再追问"现在预算多少"答 2000。
- 回归：`62 passed` 起跳，一条不掉；`/adjust` 与 `/plan` 的老用例不动。

## 8. 风险

1. 意图误判是双向的，判据里用两个比率各自卡，不承诺 100%。
2. **LLM 认得出来，但下游没有对应动作**。改方案的解析是 LLM 做的（规则路径只是它返回非 JSON 时的兜底），
   输出被限定在六个槽位：`budget` / `transportation` / `accommodation` / `preferencesToAdd` /
   `preferencesToRemove` / `extraRequirements`。"住得离西湖近一点"能装进 `extraRequirements`，
   但下游只有四个布尔开关（`relaxed_pace`/`avoid_seafood`/`wants_landmark_ceremony`/`prefers_indoor_backup`），
   且 `_select_hotel` 只按"价位惩罚 + 到当天景点中心的距离"打分，不读这些约束。
   结果就是：这句话被记录、出现在 `planningNotes` 里，但不会真的改变选哪家酒店。
   处置有两条路：一是收窄承诺（本节下面这段），二是给下游补格子（见第 9 节）。这里先走第一条：
   所以 B 的归一化不是翻译词汇，而是**只承诺下游做得到的事**：
   提示词里限定 `adjustmentPrompt` 只能落在预算/交通/住宿档位/偏好增删/节奏这五类，
   落不进去的（换位置、改天数、指定某家店）当场回答"这条我记下了，但当前版本不会改变结果"，
   不要转给 `/adjust` 让用户以为改了。
3. 模型可能在 `answer` 里说"已经帮你改好了"，而实际什么都没改：提示词里明令禁止
   （确认前不许用完成时态），判据里抽查。
4. 无回滚：改坏了只能再改一次。不做撤销，成本不值。

## 9. 扩位：给"住哪儿"补三个输入格子

这一节和第 3~6 节相互独立，可以单独排期（当作 B 的后续 B2 / C 档），但它补的正是第 8 节风险 2 里
"下游没有对应动作"那一条。

起因一句话：LLM 能听懂"住得离西湖近一点"，但听懂之后**没有格子可填**，于是这句话只能落进
`extraRequirements` 的自由文本；而真正挑酒店的函数入参只有三个
（`travel_assistant/agent/planner_agent.py:779`，参数是候选酒店、当天景点、日预算），
它连 `constraints` 都不接。所以这一节不是"让模型更聪明"，是**给模型加输入出口**。

### 9.1 三个格子

| 格子 | 字段落点（对外驼峰） | 用户怎么填 | 谁读它 | 不填时回落 |
| --- | --- | --- | --- | --- |
| 全程酒店锚点 | `TripPlanRequest.hotel_anchor` → `hotelAnchor` | 前端"期望住宿位置"一个输入框；自然语言那条由 adjust 路径写入 | 两处挑酒店的代码：先按锚点过滤候选池（见 9.3） | 现状（不过滤） |
| 按天锚点 | `TripPlanRequest.day_hotel_anchors`（对外 `dayHotelAnchors`，`{day_index: 地名}`） | 追问里说"第二天住得离西湖近一点" | 同上，当天有则只用当天的，没有再取全程锚点 | 现状 |
| 整趟同一家 / 各天最优 | `TripPlanRequest.hotel_continuity`（对外 `hotelContinuity`，`strict` \| `optimal`） | 前端一个下拉，默认 `optimal` | `build_plan` 的逐天循环：`strict` 时第 1 天选定后不再重选 | `optimal` ＝ 现状，逐天各选各的 |

三个字段都挂在 `models/trip_plan_request.py:14` 那个类上（现有字段只有
`city`/`startDate`/`endDate`/`budget`/`preferences`/`transportation`/`accommodation`/`extraRequirements`），
全部可空，`optimal` 与 `None` 等价。

第三条值得单说：现状下"第 2 天住哪"跟"第 1 天住哪"完全无关，唯一随天变化的项是到当天景点中心的距离，
所以景点一西一东就会翻天，而且天天搬行李这件事没有任何输入位能拦。把选择权做成一个下拉，
比我们在代码里硬写一个"续住加 40 分"更诚实——它把"少搬一次行李 vs 少花二十分钟通勤"这个取舍交回给用户。

### 9.2 锚点怎么变成坐标（这一步是新增成本）

地名不能直接参与算距离，得先换坐标：拿 `hotel_anchor` 发一次高德 `/v3/place/text`，
城市取 `request.city`，取第一条 POI 的经纬度。这次调用不新写客户端，直接复用
`clients/amap_http.py` 已有的 `build_candidate_urls` + `fetch_json` + `check_status`
（`amap_hotel.py:18` 和 `amap_attraction.py:17` 用的就是同一个 path）。

- 一次调用 ≈200ms，且占高德每秒配额，会和规划期的并发请求撞 `CUQPS`（已有重试可覆盖）。
- 搜不到（错别字、地名不在该城市）时：**记一条 `status=fallback` 的留痕，按没填处理**，不许抛错、不许瞎猜坐标。
- 候选酒店自身没有坐标的（`hotel.location is None`）：**不参与过滤判断、直接保留在候选池里**，
  后面仍由现有三项打分处理。理由是没法证明它在圈外就把它踢掉，会把候选池越滤越小甚至滤空。

### 9.3 生效方式：候选池硬过滤，不做加分项

**先记一次弯路**：我初稿写的是"往打分里加一项 `anchor_penalty = 到锚点公里数 × 3`"，
被一句"会不会和算分冲突"问穿了——那个形状根本不成立。三处冲突：

1. 单位撞：锚点项和现有的"到当天景点中心公里数"都是公里，一个乘 3 一个乘 1，
   同位置打架、谁权重大谁赢。我原话"只在同价位酒店之间起作用"不准确。
2. 时间撞：锚点对每家酒店是个**跨天不变的常数**，距离项每天重算。景点一挪，
   8 公里的差就盖掉 1.5 分的锚点差——填了等于没填。
3. 归属撞：格子只挂在一处打分上，另一处换店的代码看不见它（见下面第 ⑤ 行）。

同一份值在这条链路上各走一遍（杭州 3 天、总预算 3000 → 日均预算 1000，
此时价位惩罚只有 0/8 两档、质量加成不生效）：

| 步骤 | 位置 | "西湖"这一份值变成什么 |
| --- | --- | --- |
| ① | 前端输入框 | 两个字符 |
| ② | 地名→坐标 | 一次高德调用，一个经纬度 |
| ③ | `_select_hotel` 第 1 天 | 民宿 A（0 + 距离 4 + 锚点 1×3）= **7**；连锁 C（超线 8 + 2 + 0.5×3）= **11.5** → 选 A，锚点起作用了 |
| ④ | `_select_hotel` 第 2 天 | 景点挪到城东：A 距离 4→13、C 距离 2→3，**锚点那两项一分没变** → A=16、C=12.5 → 照样翻店 |
| ⑤ | `reduce_budget` 分支的 `_select_budget_friendly_hotel`（`planner_agent.py:479`） | 它的打分只有「10 分超线惩罚 + 到当天景点中心公里数」，**括号里没有锚点**，且只肯换成更便宜的 → 锚点选出来的店在这被顶掉 |

所以改成**硬过滤**：填了锚点，就先在"离锚点半径内"的酒店里跑分，跑分的三项一个字都不改。

- 过滤不参与打分，就不与任何一项抢权重。
- 过滤每天重新生效（第 2 天照样只在圈内选），不会被随天变化的距离顶掉。
- 两个写点共用同一个"取候选池"的口子：`_select_hotel` 和 `_select_budget_friendly_hotel`
  都先过这一道，第 ⑤ 行那个归属撞才真正堵上。
- 圈内一家都没有（或酒店全部无坐标）→ 回落成原候选池，记一条 `status=fallback` 的留痕，
  不抛错、不悄悄改用别的城市。
- **半径取多少先不定**（按"加分暂时不看"的口径，这轮不碰数字）。实现时拿一次真实候选池
  跑一遍分布再拍，它进第 11 节待拍板。

#### 圈只保证"一带"，不保证"最近"——圈内怎么排（原稿漏写，2026-10-08 补）

划掉圈外之后，圈内还是那三项打分说了算，**西湖远近不参与**，所以完全可能选中圈边缘那家。
原稿只写了过滤、没写这一步，判据也只卡了"在圈内"。三种排法摊开：

| 圈内的排法 | 结果 | 代价 |
| --- | --- | --- |
| A：照旧，不管远近 | 一带里最划算的那家 | 就是上面这个毛病 |
| B：只按离锚点多近排，最近的赢 | 保证贴湖 | "离当天景点近"这一维作废，通勤可能拉长四五十分钟 |
| **C（采纳）**：远近先分档，同档内走原三项打分 | 先贴湖，没有贴湖的才退一档 | 多一个档位边界要定 |

C 的形状是**分堆，不是算分**：

```
圈内的酒店 → 按"到锚点多少公里"落进档：0~1km 一档、1~3km 二档、3km~半径 三档
             从最低那档开始看：这档里有酒店 → 只把这一档交给原来那三项打分
             这档空 → 退到下一档
```

为什么不选 B：B 等于让"贴湖"这一家单独说了算，第 2 天景点在城东时它会挑一家把通勤拉很长的；
C 只在同档内部让原打分说话，档与档之间的取舍只剩"远近差多少算同一档"这一个边界问题，
**不用回答"该给几分"**——那正是加分版死掉的地方。
档位边界和半径一样，这轮不碰数字，一起进第 11 节待拍板。

第 2 天说的话只管第 2 天——每天用哪个锚点，回落顺序就三档：

```
第 i 天挑酒店时：
  1. dayHotelAnchors 里有第 i 天  → 只用那一个地名画圈
  2. 否则 hotelAnchor 有值        → 用全程锚点画圈（每天都同一个圈）
  3. 两个都空                     → 不画圈，候选池原样进打分
```

`strict` 和按天锚点会互相矛盾（一个说三天不许换店，一个说第 2 天换到西湖边），口径定死：**`strict` 赢**，
当天锚点照常记录但**不参与过滤**，并在方案里出一条备注"已锁定同一家酒店，第 2 天的位置要求未生效"。
不做静默吞掉——那正是这句话今天消失的方式。

### 9.4 `strict` 必须自带代价说明

锁同一家等于废掉"离当天景点近"这一维，第 2、3 天通勤会变长。所以：

- 预算卡不变；路线卡小字注一句"已锁定同一家酒店，比各天最优多 X 分钟通勤"，
  X 用 `_estimate_transportation_cost` 在两种选法下的差值现算，不写死。
- 不注这一句，用户只会看到"通勤怎么变长了"，会当成 bug 来查。
- **`strict` 有两个写点，不是一个**：逐天循环里除了 `_select_hotel`（`planner_agent.py:81`），
  反思驱动的重规划在 `reduce_budget` 那一支还会换一次酒店
  （`planner_agent.py:406` → `_select_budget_friendly_hotel`，它会挑一家更便宜的顶掉当天的）。
  只守第一处的话，预算一超线第二天照样换店，"整趟同一家"就是句空话。两处都要读 `hotel_continuity`。

### 9.5 与既有行为的冲突（开工前必须先拍板）

`agent/planner_agent.py`、`models/trip_plan_request.py`、`static/index.html` 三个都从早期版本沿用而来
（前端那 2905 行是逐字拷贝）。这一节会**故意偏离既有行为**，四处：

| 偏离点 | 现状 | 改法 | 影响范围 |
| --- | --- | --- | --- |
| `TripPlanRequest` 加三个字段 | 只有八个字段，没有位置/连续性 | 加 `hotel_anchor`/`day_hotel_anchors`/`hotel_continuity`，全可空 | 请求体扩展，老请求照常 |
| 两处挑酒店的代码 | 三参数、三项打分；另一处两项打分 | 入参多一个锚点坐标，先按半径过滤、再按远近分档，**同档内跑原打分，公式与常数一字不改** | 只影响进入打分的候选集合与它们的先后 |
| 一次地名→坐标的高德调用 | 无这次调用 | 有（仅填了锚点时） | 多占一次配额、多 ≈200ms |
| `static/index.html` | "期望住宿位置"输入框与连续性下拉都不存在 | 加一个输入框 + 一个下拉 + 一句代价注释 | 前端不再与早期版本逐字一致 |

按长期约束，这四条要逐条写进 `DESIGN_NOTES.md`。并且**不填新字段时的结果必须与改前逐字一致**，
这条写成回归判据（9.7 第 1 条），偏离只在用户显式填了新格子时才发生。

### 9.6 非目标

- 不改既有常数：0/8/12/24/50 那套预算惩罚、0.42/0.48/0.55 那三个阈值、质量加成的 1600/2500 档全不动。
- 不再往打分里加新项（9.3 那条弯路已作废）；锚点只决定候选集合，不决定分数。
- 不做"指定某一家酒店"（按名字直选）——那是另一格，还要把候选池换成单点查询，成本不值。
- 不在这一节让 LLM 自己发高德请求拿坐标（幻觉坐标会把整趟行程带到别的城市）；地名→坐标走确定性客户端。

### 9.7 判据

1. 不填三个新字段时，同一个 `TripPlanRequest` 改前/改后跑出的 `TripPlan`，逐天 `hotel.name` 与通勤完全一致（回归 diff 为空）。
2. `hotelAnchor="西湖"` → 每天选中的酒店都在西湖半径内（断言过滤生效，不是"分数里多了一项"），
   且落在**最低那一档**里——只要那一档有酒店。
3. `hotelContinuity=strict` → 三天 `hotel.name` 全等；总通勤 ≥ `optimal` 那次；前端出现那句代价注释。
   再加一条**把预算压到必然触发 `reduce_budget` 的值**跑一遍，断言三天仍全等（守住 9.3 表格第 ⑤ 行那个写点）。
4. `dayHotelAnchors={1:"西湖"}` → 只有第 2 天的酒店发生变化，其余两天不变。
5. 锚点地名搜不到 → 不 500、回落现状、留痕一条 `status=fallback`。
6. 候选酒店全部无坐标时，填了锚点也不报错，结果与不填一致。
7. 圈内一家都没有（半径填小到 0）→ 回落原候选池 + 留痕，且方案照常产出，不空手失败。
8. 同时给 `strict` 和 `dayHotelAnchors={1:"西湖"}` → 三天仍同一家，且方案里出现那句
   "第 2 天的位置要求未生效"的备注（断言矛盾是明说的，不是静默吞掉）。
9. 圈内跨两档（造两家：一档 0.6km、二档 2.4km，且二档那家在原三项打分里分数更低）→
   选中**一档那家**（断言分档优先于打分）；同档里放两家时，才由原三项打分决定选谁。
10. 一档空、二档有 → 退到二档并照常出方案，不回落成全城。

### 12.3 三条实测把设计改了

1. **原稿假设"候选池里有附近酒店"，实测不成立。** 杭州、3 天、3000 预算、舒适型的真实候选只有 10 家，
   到西湖距离升序是 `6.1 6.2 6.3 9.1 10.5 11.1 18.1 22.3 63.3 110.1` 公里——按 5 公里画圈必然圈空，
   "住得离西湖近一点"照样落不了地。于是补了 `/v3/place/around` 那趟周边检索（半径 5 公里拿到的是
   12m、408m、410m、414m 这一批），锚点这才真的换得出酒店。
2. **原稿没预料"逐字段拷 request"有两处。** 闭环每轮自己拷一份（`loop_planning_agent.py:_copy_request`），
   第一版只补了 `request_optimization_strategy_service.py:copy_request`，结果单测直连 builder 生效、
   走 `/plan` 完全不生效且连留痕都不出现——症状是"字段能解析（400 里报得出 `hotelContinuity`）但行为一点没变"。
   两处都补上，并各配一条"拷完还在"的用例。

3. **周边检索不能并回全局池子**。第一版把补来的 10 家并进 `hotel_result.hotels`，端到端跑出来是：
   只声明"第三天住西湖边"，第一天和第二天也跟着从全季换成了别家——补一次检索等于替全程重开了标底。
   改成"每天一份自己的候选池"（`PlannerInput.day_hotel_candidates` 只装有锚点的那些天，
   全城那份一字不动）之后，判据 4 才真的成立：那两天回到不填时的选择。

### 12.4 判据核对

| --- | --- | --- | --- |
| 不填锚点 | 全季酒店（离西湖 6.21km） | 同左 | 同左 |

景点中心 4.6 公里，比最近的一家远 3.1 公里`；第 3 天因为差距不到 1 公里，落回短句`第 3 天沿用第 1 天的酒店…`。
