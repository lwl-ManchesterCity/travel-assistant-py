## 一、已定的决策

| # | 决策 | 理由 |
|---|---|---|
| 1 | **登录挡在最前面**：不登录用不了，先登录才能开始规划 | 每一轮都天然带着 `user_id`，抽取偏好时不用另找用户身份 |
| 2 | **只把偏好落库**，方案与对话继续留在 `sessionStorage` | 方案落库是另一个大件（列表页、删除、命名），别混进这一档 |
| 3 | **偏好是一条条自由短语**，不分类 | 分类边界最后一定会打架（「怕累」算节奏还是住宿？） |
| 4 | **抽取由 LLM 判断**，不是每句话都存 | 「你好」不存，「我不能吃辣」存 |
| 5 | **注入位置是系统提示词**，不是历史 | 偏好必须每次都生效，不能让模型自己决定读不读 |
| 6 | **表单优先于长期偏好** | 用户这次明确填的，比从历史推断的更权威 |
| 7 | **存了必须看得见、删得掉** | 看不见的记忆等于没有，也删不掉记错的那条 |
| 8 | **登出时清 `sessionStorage`** | 否则 A 登出、B 登入，B 会看到 A 的方案与聊天记录 |
| 9 | 库用 **Postgres 16**，`brew services start` 开机自启 | 要跨设备；SQLite 那种单文件在多实例下会崩 |
| 10 | **分三档落地**：① 登录 → ② 记偏好 → ③ 看偏好，每档做完交你验收再进下一档 | ②要①的表、③要②的数据，顺序本来就定死；分档只是让哪一档坏了就卡在哪一档查 |
| 11 | 「我的偏好」界面 = **助手页顶栏一个入口，点开是弹层** | 与顶栏已有语汇一致；在助手页聊着天就能核对、删掉记错的 |
| 12 | **「记的那一刻」就要看得见**：第二档里，答案下面回一行「已记住：不能吃辣」，不等第三档的列表 | 第 7 条的**前半句**先兑现——用户不同意的那条当场就看见了，事后翻列表才发现要难得多 |

### 1.1 两个写入点

| | 来源 | 例子 |
|---|---|---|
| **①** | 生成方案时表单里的 **NO.3 备注**（`extraRequirements`） | 「对海鲜过敏」 |
| **②** | 旅行助手里用户说的话 | 「我不能吃辣」 |

两处都**先过 LLM 判断**，判出来的才写库。

### 1.2 LLM 要判三件事，不是一件

1. **算不算偏好？**——「你好」不算。
2. **是「这个人」还是「这一趟」？**
3. **是这个人的，还是同行的人的？**（第二档验收后补的，见 §2.2.11 末）

```
「对海鲜过敏」       → 这个人     ✅ 存
「我不能吃辣」       → 这个人     ✅ 存
「预算敏感」         → 这个人     ✅ 存
「想去看升旗」       → 这一趟     ❌ 不存
「希望路线更轻松」   → 这一趟     ❌ 不存
「我朋友对海鲜过敏」 → 同行的人   ❌ 不存
```

**只存「这个人」的。拿不准就按「这一趟」处理，不存。**

理由与提示词里「防过度推断」那条同源：**存错了会污染之后每一次规划**，
不存的代价只是这一趟没记住。两边不对称，宁可少存。

第 3 条不是第 2 条的复述，它是**规则 13 自己造出来的坑**：那条规则同时要求
「只写偏好本身、不要带主语」，于是「我朋友对海鲜过敏」剥掉主语就是「对海鲜过敏」——
**和用户本人说的长得一模一样**，模型分不出来，用户以后每一趟就都被这么带着了。
所以别人的话只能**整条丢**，**不许「去掉主语再记」**。

分界看是**谁**：同行的人是谁（「带小孩出行」）是他的情况，要记；
同行的人**自己**的口味和状况，不记。

### 1.3 抽取不额外花一次模型调用

复用 `agent/ask_agent.py` 规则 9 的 JSON 信封，加一格：

```json
{"intent":"answer","answer":"…","preferences":["不能吃辣"]}
```

判断与回答在**同一次调用**里做完。代价是"答问题"和"记偏好"耦合在一次输出里，
出问题时要一起看——这一点验收时要盯。

（写入点 ① 走的是规划那条链，不是追问信封，那里的取法待定，见 §二。）

## 二、设计

> 按 §一 第 10 条**分三档**落地，每档做完交你验收再进下一档。
> 本节按档编号，**没轮到的档不提前展开**——设计跟着实现走，免得写完就过期。

### 2.1 第一档：登录

**要做到**：打开页面进不去，必须先登录；注册、登出能用。
**偏好一个字都不碰**，现有规划 / 追问 / 改方案行为一行不改（只多一道门）。

#### 2.1.1 依赖 → `requirements.txt` 10 行变 12 行

| 包 | 干什么 | 为什么是它 |
|---|---|---|
| `psycopg[binary,pool]` | Postgres 驱动 + 连接池 | 端点全是同步 `def`（FastAPI 自动丢线程池），**用不上 asyncpg**；池子对应 Java 那边 HikariCP 的角色 |
| `bcrypt` | 密码哈希 | 直接用 `bcrypt`，**不用 `passlib`**——passlib 已停更，且与新 bcrypt 有兼容告警 |

连接串走新配置项 `TRAVEL_DB_DSN`，默认 `postgresql:///travel_assistant`：
本机 unix socket + 当前系统用户，**不需要密码**，`.env` 留了覆盖点。

#### 2.1.2 表（两张，没有偏好）

```sql
create table if not exists users (
    id            bigserial primary key,
    username      text not null unique,
    password_hash text not null,
    created_at    timestamptz not null default now()
);

create table if not exists sessions (
    token      text primary key,
    user_id    bigint not null references users(id) on delete cascade,
    created_at timestamptz not null default now(),
    expires_at timestamptz not null
);
```

**不上 alembic**。这个体量上迁移框架是负担，改成 `travel_assistant/db/schema.sql` +
启动时 `create table if not exists` 幂等建表。
**边界要记牢**：`if not exists` 对已存在的表**整条跳过**，所以**改列它一个字都不会做**——
哪天真要改列，就得引入 alembic，别指望它。

#### 2.1.3 密码 → bcrypt，且**必须卡 72 字节**

- 存 `bcrypt.hashpw(password.encode("utf-8"), bcrypt.gensalt())`，盐由 bcrypt 自己生成。
- **bcrypt 只看前 72 字节**：超长密码后面的部分等于不存在，新版更是**直接抛异常**。
  所以校验里硬性 `len(password.encode("utf-8")) <= 72`——**按字节算，不是按字符**
  （一个汉字 3 字节，24 个汉字就到顶了）。
- 下限 6 字符。用户名去首尾空白后 2–32 字符、不含空白。

#### 2.1.4 会话 → httpOnly cookie + `sessions` 表

选 cookie，不选「JWT 放 localStorage」：

| | cookie + 会话表 | JWT 放 localStorage |
|---|---|---|
| XSS 偷不偷得走 | **偷不走**（httpOnly） | 偷得走，JS 直接读 |
| 能不能真的登出 | **能**（删一行） | 不能，只能等它过期 |
| 要不要多存一行 | 要 | 不要 |

登录成功 → `secrets.token_urlsafe(32)` → 插一行 `sessions`（有效期 30 天）→
`Set-Cookie: travel_session=<token>; HttpOnly; SameSite=Lax; Path=/; Max-Age=2592000`。

- **`SameSite=Lax`**：同源应用够用，顺带挡掉外站发起的跨站 POST。
- **`Secure` 现在不能开**——本机是 http，开了浏览器直接不收。**上线必须开，记在这里别忘。**
- 不用 JWT 就不用签名密钥，`.env` 除了 DSN **不加新键**。

#### 2.1.5 端点（全在 `/api/auth` 下）

| 方法 | 路径 | 干什么 |
|---|---|---|
| POST | `/register` | 建号，**成功后直接登录**（种 cookie），省用户再输一次 |
| POST | `/login` | 种 cookie |
| POST | `/logout` | 删 `sessions` 那一行 + 清 cookie |
| GET | `/me` | 200 回 `{username}`；没登录 401。**前端开页面先打这个，决定显示哪一屏** |

**错误文案不区分"用户名不存在"和"密码错"**，统一说「用户名或密码不对」——
分开说等于替攻击者把有效用户名筛出来了。

#### 2.1.6 挡谁 → 只挡 `/api/trips/*`

`/plan`、`/adjust`、`/ask`、`/ask/stream` 四个挂 `Depends(require_current_user)`。

**`/api/map/config` 不挡**：它吐的是高德**前端 JS key**，那个 key 本来就要发到浏览器里用，
挡它没有任何意义。挡的判据是"会产生成本、会读写数据"，不是"是个 API"。

401 走项目统一的 `ApiErrorResponse` 信封（`code="UNAUTHORIZED"`），
**不直接用 FastAPI 的 `HTTPException`**——那个回 `{"detail": ...}`，跟别处长的不一样。

#### 2.1.7 前端

- `index.html` 加一整屏 `#login-page`。**登录和注册是两屏，靠底部一行链接互切**，
  不是并排两个按钮：并排的话屏上永远长一个样，用户点完「注册新账号」
  不知道自己进没进注册界面（用户原话）。切换时**标题、说明、主按钮、链接四处一起变**
  （`auth.js` 的 `MODES` 表），"我现在在哪一屏"一眼可见。
- **品牌名在卡片外面、上面**（`.login-shell` 是"品牌 + 卡片"的竖列，两者同宽对齐）。
  它说的是"这是哪个产品"，卡内那行标题说的是"这是哪一屏"，两件事分开站。
  字号照抄落地页的 `.doc-title`（得意黑、32px、粗体）——**同一个产品两张脸最容易露怯**。
  卡内模式标题是卡内最大的一行，用海蓝跟上面的墨色品牌名分开。
- **整卡居中**（`text-align: center`），但输入框里的字**留在左边**：打用户名时字跟着居中会左右晃，
  一个字一个字挪位置，看着像在抖。所以 `.login-form .input` 单独拉回 `left`。
- **说明那行按屏给**：登录屏**不给**（"已有账号？填用户名和密码继续"是废话，人站在登录屏就说明有账号），
  注册屏给（那里要交代用户名与密码的规矩）。空文本时整行 `hidden`，否则 margin 还在、会多一道空白。
- **密码框里有个小眼睛**：密码打错了只能整条重打，这是登录页最常见的一次挫败。
  切换 `type` 会让光标跳回开头（浏览器重建了那个控件），所以**手动把光标放回末尾**，
  否则点完眼睛接着打字，字会插到最前面去。换屏时收回眼睛。
- **开页面第一件事是 `GET /api/auth/me`**：200 显示规划页，401 显示登录页。
  规划页在确认之前**一直藏着**——不能先闪一下再挡住。
- 登出：`POST /api/auth/logout` → `clearSession()`（清 sessionStorage）→ 回登录页。
  **这就是 §一 第 8 条**：不然 A 登出、B 登入，B 会看到 A 的方案和聊天记录。
- **登录成功也要 `clearSession()`**：换人了，上一个人的东西不能留在浏览器里。
- 放进新文件 `static/js/auth.js`，**在 `app.js` 之前**加载（门先于内容）。

#### 2.1.8 测试怎么分层（这一条最关键）

现有 339 条是**纯单元测试、不碰外部依赖**，不能因为这一档把它们变成"必须先起 Postgres"。

**照项目已有的做法**：`clients/` 下每个高德实现都配一个 `RuleBased*` 兜底、共用同一个接口。
这里照抄——`AuthStore` 一个接口、两个实现：

| 实现 | 谁用 |
|---|---|
| `InMemoryAuthStore` | 单元测试、探针 stub |
| `PostgresAuthStore` | 真服务（`container.py` 装配） |

- **单元测试**直接 `AuthService(InMemoryAuthStore())`，不碰库，339 条一条不受影响。
- **真 SQL** 单独一个 `tests/test_auth_store_postgres.py`，**连不上就 skip**，不拖累默认 `pytest`。
- **端到端**由 Playwright 探针跑真服务 + 真库，覆盖"注册 → 登录 → 登出 → 再访问被挡"整条。

| 9 | 密码超 72 字节 | ✅ 回 400 + `VALIDATION_ERROR`，details 里说明按**字节**算 |

**落地时踩到的坑（记一笔）**

- **测试夹具里 `lambda: AuthService(InMemoryAuthStore())` 是错的**。FastAPI 每次请求都调一遍
  这个 lambda，等于每条请求一个**空 store**：注册完那条用户下一条请求就查不到了。
  要先把 service 建好、lambda 只负责返回它。三条用例因此红过。
- **409 的 `details` 一度写成 `f"username: {exc.username}"`**，前端错误提示优先读 details，
  于是用户看到「username: amy」——把机器字段当人话显示了。现在写的是完整的那句话。
- **psycopg3 默认走扩展查询协议，一次只允许一条语句**。`schema.sql` 是多条（还带注释），
  必须用 `psycopg.ClientCursor`（简单查询协议）才能整份发过去。
- **bcrypt 5.x 对超过 72 字节的密码直接抛 `ValueError`**（实测：`hashpw(b"a"*100, …)`）。
  所以那条按**字节**的校验不是"保险起见"——不加的话 100 字符的密码会变成 500 而不是 400。
  而且必须按字节：一个汉字 3 字节，24 个汉字就到顶。
- **`psycopg_pool` 的 `open` 参数默认值将来会从 `True` 变成 `False`**，所以显式写了 `open=True`。
  它不会让应用启动时连库——`_build_pool()` 只在第一次 `get_pool()` 时才被调到。
- **app.js 是脚本顶层声明、没有 IIFE**，`const landingPage` 这些名字已经占了全局词法环境。
  auth.js 再写一遍同名 `const` 会直接 `Identifier has already been declared`、**整份脚本不执行**。
  所以 auth.js 自己包了一层 IIFE。
- **登录页第一版是"并排两个按钮"，被用户当场否掉**：点「注册新账号」之后屏上什么都没变，
  用户不知道自己进没进注册界面。改成两屏互切 + 各自的标题。教训是
  **"两个按钮做同一组输入框的两件事"会藏掉"我在哪一屏"这个信息**，
  而那个信息比按钮本身重要。
- **品牌名第一版压在卡内当 14px 小字**，用得意黑（标题体）——那个字体的设计尺寸是大标题，
  14px 下斜着挤成一团，既看不清也压不住场（用户反馈「字体优化一下」）。移到卡外、按 `.doc-title`
  的 32px 重排。教训是**标题体不能拿来当正文用**，它在小尺寸下不是"小一号的标题"，是"看不清的字"。
- **账号区第一版是 14px 灰字 + 12px 小钮**，扫过去看不见（用户反馈「这部分内容放大一点，看不清了」）。
  用户名是页头上唯一回答"我现在是谁"的东西，却和旁边的备注文案一个分量——
  提到正文级字号 16px + 墨色 + 中等字重，登出钮跟着从 12px 提到 14px。
  教训是**一行的两件东西差两级字重，看起来像是没对齐**。
- **探针的「没有 JS 报错」把浏览器对非 2xx 的网络日志也算进去了**。
  这个探针**故意**打了好几次 401/409，于是那条判据永远是红的、等于没有。
  现在滤掉 `Failed to load resource`，只留 `pageerror` 与真正的脚本 error。

### 2.2 第二档：记偏好

**要做到**：两个写入点都能把「这个人的」偏好落库、重复的不落、系统自己生成的句子不落；
下一次规划与下一次追问都真的用上它；**记的那一刻用户看得见**。
**不做界面**：列出与删除是第三档（§2.3）。本档结束时你只能靠"回答下面那一行小字"和 `psql` 验收。

#### 2.2.1 表（第三张）

```sql
create table if not exists preferences (
    id         bigserial   primary key,
    user_id    bigint      not null references users (id) on delete cascade,
    content    text        not null,
    source     text        not null,
    created_at timestamptz not null default now(),
    unique (user_id, content)
);
```

- **去重交给库**：`unique (user_id, content)` + `on conflict do nothing`。与第一档 username 同一个招——
  一条语句里完成"判重 + 写入"，不用先查后插（那中间有窗口，两次请求同时到就会进去两条）。
- **不建 `updated_at`**：偏好没有"修改"这个动作。要改就删掉说条新的（第三档的删除），
  或者直接说一条新的覆盖——留 `updated_at` 等于鼓励"就地改"，而"就地改"最难的是判断哪条该被改。
- **留 `source`**（`form` / `chat`）：记错的时候第一个要问的就是"这条哪来的"。
  两个写入点的输入长得完全不同（一个是表单自由文本、一个是聊天原话），出问题时靠它定位。
- **不另建索引**：注入时那句 `where user_id = %s` 走 `unique (user_id, content)` 的最左前缀。

#### 2.2.2 Store 与 Service（照 §2.1.8 的分层再抄一遍）

| | |
|---|---|
| `PreferenceStore` | 接口：`add(user_id, content, source) -> bool`（False＝已经有一条了）、`list_for_user(user_id) -> list[PreferenceRecord]` |
| `InMemoryPreferenceStore` | 单元测试、探针 stub |
| `PostgresPreferenceStore` | 真服务（`container.py` 装配） |
| `PreferenceService` | `record(user_id, contents, source) -> list[str]`（**只返回真正新存进去的**）、`list_for_injection(user_id) -> list[str]` |

**规范化（进库前都过一遍）**：strip；去掉尾部标点；**超过 40 个字符的丢掉**；
一次最多取 5 条；同一个 user 最多留 **50 条**（满了丢弃并在留痕里记一笔）。

- 40 字符那道闸门不是洁癖：模型偶尔会把用户整句话当偏好吐出来
  （「我希望这次去杭州的时候能顺便看看西湖」）。那不是偏好，是一条被截断的行程要求，
  存进去之后**每一次**规划都会被带上。
- 50 条上限是因为偏好**进每一次 prompt**，没上限的话话多的用户（或一次注入攻击）
  能把系统提示词撑爆。

#### 2.2.3 写入点 ②：追问那一格

复用 §1.3 说的那个信封，加一格：

```json
{"intent":"answer","answer":"…","preferences":["不能吃辣"]}
```

规则 9 只管格式，**判据要另写一条规则 13**（§1.2 那三条）：

- 只记**这个人的**：「对海鲜过敏」「我不能吃辣」「预算敏感」；
- **这一趟的不记**：「想去看升旗」「这次轻松点」；**拿不准就按"这一趟"不记**；
- **只记用户本人的**：同行的人自己什么口味、什么状况，整条不记
  （「我朋友对海鲜过敏」）；**不许「去掉主语再记」**——见 §1.2 第 3 条；
- 与行程无关的闲聊不记（「你好」）；
- 一句话里可以有多条：「我不吃辣也不吃香菜」→ `["不吃辣","不吃香菜"]`；
- **没有就交空数组，不要为了填而填**。模型天然倾向于"总得输出点什么"，这句必须写死。

解析走 `_Decision`，清洗照抄 `_pin_hints` 那套（str / list 都收、strip、去重）。
**这条链不加新的回落逻辑**：信封解析不出来就是空数组，不记。

用户身份从哪来：`ask_controller.py` 现在写的是 `dependencies=[Depends(require_current_user)]`
（那一行上面的注释已经预告了这一档要改）。改成参数 `user: AuthUser = Depends(require_current_user)`，
把 `user.id` 传进 `ask_agent.ask(...)`。两条追问端点（一次性与 SSE）都要传。

#### 2.2.4 写入点 ①：表单备注，且**必须剔掉系统自己加的句子**

复用 `RequirementAnalysisService` **已经有的那次**模型调用（§1.3 的规矩：不额外花一次）。
它的 system prompt 本来就收到了 `extra_requirements` 全文、本来就在吐 JSON，加一格 `"preferences": []`
是零边际成本。抽取结果挂在返回的 `PlanningConstraints` 上（加一格 `extracted_preferences`），
由 `PlannerInputBuilder.build()` 交给 `PreferenceService`——**调用点只有这一个，
规划和改方案两条路都经过它**（`adjust_trip` 最后也是 `plan_trip`）。

**为什么不在控制器层抽**（那里拿得到干净的用户原文，看着更省事）：
代价是每次规划多一次模型调用。规划本身 40~70 秒，但用户对"多转一次圈"是有感的，
而"输入被污染"这件事在下面用十行就能洗掉。

**被污染的是什么**：`RequestOptimizationStrategyService` 会往 `extra_requirements` 里
**追加系统自己生成的句子**（「整体控制预算，优先保留高价值景点」等，见
`_apply_reduce_budget` / `_apply_compress_route` / `_apply_indoor_replacement` / `_apply_upgrade_experience`）。
改方案走的是 `plan_trip(decision.updated_request)` → builder → analyze，**所以这些句子必然出现在抽取的输入里**。
它们是**这一次**的调节，不是这个人的偏好——存下来等于从此每趟都强制压预算、每趟都压缩路线。

做法：把那些写死的句子收成一个模块级常量集，抽取前**按子句精确匹配**剔掉。
它们是用 `；` 拼进去的原文（`merge_extra_requirement`），而拆分用的 `_CLAUSE_SPLIT_PATTERN`
正好按 `；;换行` 切，所以**精确相等**是成立的，不需要模糊匹配。

**失败即不记**：`analyze` 本来就有"任何异常退回规则"的兜底；写库那一下也单独 try/except 吞掉。
**记偏好是搭便车的乘客，不能让它把车开翻**——规划失败和偏好没记住，代价差着一个量级。

#### 2.2.5 注入：两个链各一个点，都进"系统提示词"的位置

**追问链** —— 每轮把偏好拼成一条 `SystemMessage` **顶在消息列表最前**（§一 第 5 条）。

- 为什么不改 `create_agent(system_prompt=…)` 那个参数：它在 `create_agent` 时就固化了，
  而 `AskAgent._agent` 是**缓存的**；按请求重建 agent 等于每轮把图重新编译一遍。
- 为什么不塞进历史：历史是**可以不被读**的（模型能选择性忽略），而且历史有窗口
  （`_HISTORY_MAX_TURNS`），偏好会被裁掉——那就等于"有时生效有时不生效"。
- 这一段里还要写死一条：**长期偏好与方案内容冲突时，指出冲突，不许默默按方案说**。
  （方案里排了一家辣菜馆，而这个人记着不能吃辣 → 要说出来，不能顺着方案讲"这家不错"。）

**规划链** —— 只动 `RequirementAnalysisService` 的 system prompt：
在里面加一段「这个人的长期偏好」原文，让模型**折进它本来就要输出的那 4 个布尔与 tags**。
再给 `LlmNarrationService` 的总览 prompt 加一行，让文案层面也能体现。

**不合并进 `request.preferences`**：那一格是"用户这次填的"，`/adjust` 会把它原样回显给前端
（`updatedRequest`）。混进去的话，用户会看到自己没填过的偏好；而且第三档的删除也删不干净——
删了库里那条，回显里还留着。

**这一档的极限，说在明处**：长期偏好对规划起作用，是**经由需求理解那 4 个布尔**
（慢节奏 / 避海鲜 / 仪式感 / 室内备选）传导的，不是逐字进规划器。所以
「对海鲜过敏」生效，「喜欢安静」这类**没有对应布尔的，影响不到规则规划器**——只会进总览文案。
真要逐条生效，得先给偏好加标签、再让规则规划器认标签，那是这档之后的事（§2.2.10）。

#### 2.2.6 「表单优先」只能是一条给模型的指令

§一 第 6 条落地时发现：**没法用代码判**——「想吃海鲜」和「不吃海鲜」哪个压得住哪个，
字符串比对做不出来（同义、反义、条件式都判不了）。所以它只能是**注进 prompt 的一句规则**：

> 本次表单里明确写的优先；与这里的长期偏好冲突时，按本次的来。

两处注入（追问链的 SystemMessage、需求理解的 system prompt）都要带这句。

#### 2.2.7 「记的那一刻」就要看得见

`AskResponse` 加一格 `recorded_preferences`（**本次真的新存进去的**），前端在答案气泡下面
回一行小字「已记住：不能吃辣」。

- 这是 §一 第 7 条（存了必须看得见、删得掉）的**前半句**，不等第三档。
  用户不同意的那一条，当场就看见了；事后翻列表才发现要难得多。
- **只报新存的**，重复说的不报。每次都弹「已记住」会变成噪音，用户会开始无视它——
  那比不显示更糟。

**落地时对设计做的几处修正**（都是实现时才看得出来的）：

1. **注入原文进的是用户提示词，不是 `_SYSTEM_PROMPT`。** §2.2.5 写的是"只动 system
   prompt"，但那是个**模块级常量**，而偏好是每人每趟不同的。拆成两半：**规则**
   （判断标准、「表单优先」）在 system prompt 里，**事实**（具体哪几条）在 user prompt
   里。同一次调用，位置不影响模型读不读得到。
2. **那一格叫 `extractedPreferences` 不叫 `preferences`。** 用户提示词里本来就有一行
   「偏好：自然风景」（表单勾的），同名会让模型把勾选框回吐成"这个人的偏好"。
   `extractedTags` 是它的兄弟字段，跟着它走。
3. **还加了一道代码闸门**：抽出来的条目若与 `request.preferences` 里的勾选项**精确相等**
   就丢掉。模型仍可能回吐，规则拦不干净；而这条恰好是用户亲自纠正过的
   （§1.1——写入点只有备注和助手输入两处，勾选框不是）。
4. **`RequirementAnalysisService.analyze` 收的是偏好**列表**，不是 `user_id`。**
   §2.2.4 说注入在需求理解里，但"注入了几条"这条留痕（判据 7）要能**证明**注入发生过——
   只有拿到同一个列表才证得了。所以由 `PlannerInputBuilder` 取一次、留痕、传下去。
   它同时也不再需要 `preference_service`，少一个依赖。
5. **`PreferenceService.record` 返回 `RecordResult` 而不是 `list[str]`。** §2.2.2 的
   `list[str]` 表达的是"只返回真正新存进去的"，那条照旧（`.added`）；多出来的
   `dropped_for_cap` 是 §2.2.2 末句要的那条留痕——上限是"系统没照做"，与"用户说的是
   哪几条"不是一回事，混进 `added` 会被前端显示成「已记住」。
6. **总览文案没单独穿一次 `user_id`。** §2.2.5 说给 `LlmNarrationService` 加一行，
   实际是把偏好写进 `planning_notes`——它本来就是总览 prompt 的一格（`规划备注：`），
   顺带其他看备注的地方也看得到。只在 prompt 要求里加了一条"确实影响到本趟时才提"。

**落地时踩到的坑**：

- **`REQ_UPGRADE_QUALITY` 抄错了一个词**（`景点丰富度` 写成 `丰富度`）。把策略句收成
  具名常量时才发现——**这正是收常量的意义**：写错的那版会让精确剔除对不上，
  而这条句子从此变成一个人的永久偏好。教训与 §2.1.10 同一条：字面量只许有一份。
- **上限检查曾排在判重之前**：库满了之后又说一遍已经有的，被记成"丢弃 1 条"。
  顺序必须是**先判重、再判上限**——重复不是溢出。测试逮到的。
- **`RecordResult` 一开始写了 `frozen=True`**，而 `record` 要往里累加。去掉。
- **测试里手写的"很长的一句"其实只有 35 个字**，40 字符闸门压根没触发，测试却是绿的。
  现在那条用例自带 `assert len(too_long) > MAX_CONTENT_CHARS`。
- **`id(object())` 当唯一后缀会撞**：CPython 复用刚释放的地址，前一条用例的对象回收后
  下一条拿到的 id 可能一模一样。改用 `itertools.count()`。
- **探针从 `/tmp` 跑会读不到 `.env`**（配置按 cwd 找），表现是"追问能力需要可用模型"，
  看着像模型的问题。必须在项目根目录跑。
- **`AskRequest(history=[AskTurn(...)])` 会被静默丢掉**：`_drop_malformed_turns` 只认
  dict。这是**既有行为**（那个校验器是照 JSON 入参写的），没有内部调用方这么用，
  本档不动它；写测试时要按线上那种 dict 形状给。
- **探针不能把模型的措辞写死**：问「我不能吃辣」，模型按规则 13 规范化成「不吃辣」——
  那是对的（"只写偏好本身、不要带主语"）。第一版探针钉死原话，红了两条。
  探针验**管道**（回的那行 == 库里那行、来源对、内容说的是那件事），措辞归模型。

**验收后补的一条：规则 13「只记用户本人的」（同日补上，随本档一起提交）**

复核规则 13 时发现它只分「这个人的 / 这一趟的」两档，漏了**别人的**。
判据进 §1.2 当第三条轴、进 §2.2.3 的规则 13 列表，措辞进 `ask_agent.py`。

- **验证只放在探针，不补单元测试**：这条判断是模型做的，而单元测试用的
  是 stub 图——喂什么出什么，它只能证明「信封里是空数组时库里不增」，
  证明不了模型判得对。判据 2/3 本来就是这么分的（`tests/test_ask_agent.py`
  的 `test_shouldRecordNothingWhenTheEnvelopeSaysSo` 就是自己喂了个 `[]`）。
- **探针那条用例的内容挑「海鲜」，不挑「辣」**：库里此刻已经有一条辣的了，
  模型万一照记，**去重会把第二遍吞掉**——用例就会为了让错的原因通过。
  （判据 2 用的是「升旗」，同一个道理。）
- 用例多钉了一条「这句照常产出回答」：模型压根没回答时，上面两条也会空过。
  判据 1 那个「链没通就停」的前置守卫管不到这里。

- 出参模型放进新文件 `models/preference.py`，照 `models/auth.py` 那个样子
  （`CamelModel`，删除回执仿 `LogoutResult`：**有个字段而不是空 200，前端好判断**）。

#### 2.3.2 列表那一格要补上 `id`

`PreferenceRecord.to_payload()` 现在只回 `{content, source}`，删除需要一个**稳定的键**：

- **用 `id` 不用 `content`。** 两个都能唯一定位（表上有 `unique (user_id, content)`），
  但 `content` 是给人看的那一份、经过模型规范和清洗，而 `id` 是主键——
  按它删没有"前端显示的那串跟库里那串是否逐字相同"这个隐忧。
- `source` 一并回给前端**并且显示**：第 7 条要的是"**记错的那条**删得掉"，
  而用户判断哪条记错了，第一个线索就是"这条哪来的"——与 §2.2.2 留 `source`
  是同一个理由，只是这次是给用户看，不是给排查的人看。
- **不回 `created_at`**：界面上不显示，服务端也没有要它对齐的场景。
  给前端没人用的字段等于多一个将来要维护的兼容面。

#### 2.3.3 删除的语义

- 一条 SQL：`delete from preferences where id = %s and user_id = %s`。
  **`user_id` 必须进 `where`**——这一档**唯一的安全面**就在这里：`id` 是连续
  `bigserial`，漏了这个条件，任何一个登录用户能删光全站的偏好，
  而且**不会有人发现**（界面上他只是在删自己的）。
- 删别人的 / 已经不存在的 → **200 + `deleted: false`**，既不报 404 也不报 403：
  - 与 `POST /api/auth/logout` 同一条理由（§2.1.5 的注释）：幂等操作报错，
    只会让前端多写一个分支；
  - 更要紧的是**不区分**。「不存在」和「不是你的」分成两种回法，等于给攻击者
    一个"这个 id 存在"的探针——那正好是 §2.1.5 不区分"用户名不存在"与"密码错"的
    同一个理由。
- **删完不做任何额外动作，也不许加缓存。** 注入是每轮**现读**的
  （`list_for_injection` 在每次追问、每次 `build` 时读库），所以删掉的那条
  下一趟就不带了。**一缓存就要处理失效，而失效漏掉的表现正好是"删了还在用"**——
  界面上那条确实没了，用户不会知道它还在生效。
- **删除走 `PreferenceService.forget(user_id, preference_id) -> bool`，控制器不直接碰 Store。**
  删除既没有清洗也没有上限，直接写 Store 看着更省事——但那是"两条链都只经过 Service"
  这个约束的**第一个口子**（见 `preference_service.py` 开头）。规矩破一次，
  下一个改动就有先例了。

#### 2.3.4 界面

- **入口在助手页顶栏**（`.assistant-top`，标题右边一个 `ghost-button`「我的偏好」）。
  为什么在助手页而不是结果页顶栏：偏好就是在这儿聊出来的（§一 第 11 条已定），
  核对它的地方该是产生它的地方——用户刚说完「我不能吃辣」，抬眼就能确认记成了什么。
  窄屏那行左边是「← 返回方案」、中间是标题，入口靠右，三个东西各占一块，不挤。
- **弹层沿用 `.adjust-prompt-overlay` 那一套**（同一个墨蓝遮罩 + 白卡 + `shadow-pop`
  + 圆角；Esc 关、点遮罩关——`app.js` 里那个弹窗就是这么写的）。
  一个新弹层长得像另一个新弹层，用户就得重新认一遍；**页面上只该有一种"弹出来"的长相**。
- 弹层内容：标题「我的偏好」+ 一行说明 + 列表 + 每行右侧「删除」。
  - **说明那行不写废话**（§2.1.7 的教训）。要交代的是这个弹层**存在的理由**：
    「这些是你以前说过的，以后的每一趟都会带上」——用户才知道自己删的不是这一趟的东西。
  - **空态不是空白**：「还没有记住任何偏好」+ 一句怎么产生一条
    （「在聊天里说一句『我不能吃辣』，或者填在备注里」）。
    **空态是本档最常见的第一次打开**——弹层打开是空的，用户得知道自己没找错地方。
  - 每行左边是 `content`，用**正文级字号**、不用小字——这一行就是这个界面的全部内容
    （§2.1.10 那条"一行的两件东西差两级字重"的教训）；下面一列灰字写来源
    （「来自聊天」/「来自表单备注」）；右边一个删除钮。
  - **删除当场生效**：点了就从列表里消失，不等刷新；删掉最后一条**回到空态**
    （而不是留一个空列表）。
- **不给编辑钮。** §2.2.2 已经定了"偏好没有修改这个动作"——要改就删掉、再说一条新的。
  就地改最难的恰恰是"判断哪条该被改"，给个编辑钮等于把这个难题丢回给用户。

#### 2.3.5 测试怎么分层

| 层 | 守什么 |
|---|---|
| `tests/test_preference_controller.py`（新） | HTTP 层：**拿别人的 id 删不掉，且自己那条还在**；删不存在的不报错、回 `deleted:false`；列表只回自己的、按写入先后；`items` 里带 `id`。挂 `without_login_gate` 夹具 + `InMemoryPreferenceStore` |
| 同上，**不挂夹具的那一条** | 未登录打这两条 → 401 且是统一信封。夹具一挂门就摘了，所以这条得单独写（照 `test_auth_controller.py` 的做法） |
| `tests/test_preference_service.py`（增） | `forget` 只删这个人自己的那一条，回 `False` 时库里原样 |
| `tests/test_preference_store_postgres.py`（增） | 真 SQL 那句 `where id and user_id`；连不上就 skip |
| `/tmp/preference_probe.py`（增一段） | 真服务 + 真库走完：说一条 → 列表里看得见 → 删 → 列表里没了 → **再说一遍又能记上** |

**最后那条"再说一遍又能记上"是本档最容易被漏掉的判据**：删不干净（改成软删、
或唯一键还占着位置）时，界面看起来完全正常，代价是这个人**再也记不上这一条**了。

#### 2.3.6 验收判据（第三档）

| # | 判据 | 怎么测 |
|---|---|---|
| 1 | **看得见** | 说一句「我不能吃辣」→ 顶栏点开弹层，里面有一条，来源写「来自聊天」 |
| 2 | **删得掉** | 点删除 → 那一行当场消失；关掉再打开，仍然没有 |
| 3 | **删了就真的不用了** | 删掉之后再生成一次方案（或追问一次），回答与留痕里不再体现它 |
| 4 | **删干净了能重记** | 删掉之后再说一遍同一句 → 又能记上 |
| 5 | **删不掉别人的** | A 登录，拿 B 那条的 id 打 DELETE → `deleted:false`；`psql` 里 B 那条**还在** |
| 6 | 未登录打不进去 | 未登录 `GET /api/preferences` → 401，且是统一信封 |
| 7 | 空态 | 新用户点开 → 空态文案，不是空白弹层 |
| 8 | 不回归 | 436 条全绿；探针全过 |

判据 3 是本档**唯一能证明"删除真的生效"**的手段——只看界面看不出来：
删掉的行确实不见了，但它还在不在生效，只有再跑一次规划/追问才知道。

#### 2.3.7 本档不做

1. **不做编辑**（§2.2.2）。
2. **不做"全部清空"、不做分页与搜索**：上限就 50 条（§2.2.2），弹层滚一下就到底了。
3. **不给偏好分类、不加标签**（§一 第 3 条）。
4. **不动注入语义**：还是 §2.2.5 那句——长期偏好对规划起作用是经由需求理解那 4 个布尔
   传导的，「喜欢安静」这类没有对应布尔的，删不删都影响不到规则规划器。
5. **不在弹层里显示记下的时间**（§2.3.2）。

## 三、明确不做

1. **不碰预算结余那条**。它是 planner 的业务改动（预算从"上限"变成"目标"），
   与本文无关，用户明确"怕改乱"，先放着。
2. **方案与对话不落库**（§一 第 2 条）。
3. **偏好不分类**（§一 第 3 条）。
4. **不做 Episodic / Procedural 两类记忆**。LangChain 参考 CoALA 把长期记忆分三类，
   但这里只用得上 **Semantic（事实）**：
   - Episodic（经验）= 会话历史 → **短期记忆已经覆盖**
   - Procedural（规则/做事方法）= 提示词里那 12 条 → **写在代码里，不该由模型记**

## 四、环境与遗留

- **Postgres 16.15 已起（`brew services start postgresql@16`，开机自启），
  库 `travel_assistant` 已建**。连接串默认 `postgresql:///travel_assistant`

- `/tmp` 里三个探针还是临时的：`multiturn_frontend_probe.py`、`assistant_stream_probe.py`、
