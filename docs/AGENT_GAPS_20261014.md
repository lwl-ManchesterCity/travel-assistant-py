## 一、一句话口径

**这个项目已经是 agent 项目了。** 差的是「能证明它好」的那一层，不是「看起来更像 agent」的零件。

具体说：它有真·工具调用（`create_agent`，两处）、真·检索（BGE-M3 + Chroma，"能用确定条件筛的绝不交给向量"）、
真·反思闭环（reflection → critic → 改 → 再判），还有人在环（追问、改方案确认、锚点钉子）和
模型不可用时的降级路径。**这些都不是"像"，是真的。**

它没有的是：**改完之后你没法知道是变好了还是变坏了。**

## 三、四条差距

### 1. 评测集 —— 最大的那个，也是唯一建议现在做的

**它具体是什么**：一个文件，几十条「问句 + 期望结果」，跑一个脚本 → 真模型、真库 → 逐条对答案 → 报分。

```
问：我不能吃辣          期望：记一条「不吃辣」
问：我朋友不吃辣        期望：不记（别人的口味不是他的）
问：你好               期望：不记
问：我想去看升旗        期望：不记（这是"这一趟"）
问：这次想轻松点        期望：不记
```

**为什么现在没有**：

现有 436 条测试回答的是「**代码有没有按写的跑**」，不是「**跑出来的东西对不对**」。
它们喂的是**桩模型**（写死返回一段 JSON，见 `tests/test_requirement_analysis_service.py` 的
`_StubLlmClient`），真模型根本没参与。

所以下面这些测试**全绿也说明不了任何事**：

- 「拿不准就按这一趟的不记」这句会不会让模型变得太保守，把「我不吃辣」也漏掉？
- 新加的「只记用户本人的」那条，模型是真守住了还是当没看见？
- 「表单优先」那条注入规则，模型到底有没有照做？

**这一轮就是活例子。** 我们动了三处提示词（规则 13、长期偏好注入块、叙述第 4 条），
验的方式是「开浏览器抽几条眼睛看」。

> **订正（2026-10-14，复核后）**：这里原来写的是「探针那 12 条是**管道验证**，
> 不是质量验证」——**说重了**。那个探针跑的是**真模型**，判据 2（这一趟的不记）、
> 判据 3（闲聊不记）、规则 13 那条（别人的不记，现共 16 条）验的**确实是判断力**。
> 它真正缺的是另外三样：**覆盖是手挑的十几条**、跑完只给「全过 / 没过」而
> **不给一个可比的分**、而且**住在 `/tmp` 里没进仓库**。
> 所以它是**冒烟测试，不是回归套件**——能说「现在大概是好的」，
> 不能说「这次改的比上次好还是差」。

**最小形态**：

- `evals/questions.yaml`：30~50 条，覆盖五类（记偏好 / 不记 / 闲聊 / 要改 / 只要答）
- `evals/run.py`：起真服务，逐条发问，对答案，打印「38/50 过」和**没过的那几条原文**
- 判分先人工看一眼即可，不必上模型裁判

> **已建成（2026-10-16）。** 实际落了 40 题 / 9 类，判分拆到 `evals/judge.py`，
> 另有 `tests/test_evals.py` 17 条钉住判分引擎本身。第一次跑 **39/40**，
> 唯一那条红是真红：裸问「灵隐寺门票多少钱」答对（查库给 30），加个「它」变成多轮指代后
> 改去读方案、答了方案里的估算值 45。根因是规则 11(c) 那句「景点在不在方案里都一样」
> 埋得太深——(c) 开头写着「或**方案里没有的**景点」，景点在方案里时模型读的是 (a)。
> 已把例外挪进 (a)，`evals/questions.yaml` 第 12 题留作回归。修完 **40/40**。
>
> 判分的一条硬规矩：**优先看结构化字段**（`intent` / `recordedPreferences` / `traces`），
> 不得不读答案时写成否命题。理由见 `evals/judge.py` 开头——探针判据 5 连踩三回，
> 全是栽在猜模型的措辞上。
>
> 另一条：**每题必须从干净上下文起跑**（`evals/run.py` 的 `_forget`）。40 道题共用一个
> 账号时，长期偏好会一轮轮攒下来，后面的题是在被前面污染过的上下文里答的。第一次跑就
> 露了马脚——第 34 题的答案里凭空冒出一句「你记着的…带小孩」，而那题压根没人提过。
> 串味会让分数两头都不准：一道题答错可能带崩后面几道，看着像另一个功能坏了。

**做的意义**：往后每次动提示词，心里有底。**这是第 2、4 条的前提**——没有它，那两条都无从验收。

### 2. 成本账

**它具体是什么**：在 traces 上多几个字段，或单独一张表，记每次模型调用的 token / 秒数 / 估算费用。

**为什么现在没有**：

`agent_traces` 记的是「**干了什么**」——比如
「PreferenceService · 注入并记录长期偏好 · 长期偏好：2 条」。
它不记「**花了多少**」。

**为什么 agent 项目特别需要**：

普通接口的成本是固定一次调用。agent 是**循环**的，成本是「转几轮 × 每轮多少」：

- 一趟规划走 loop：批判 → 改 → 再判，可能转 3 轮 = 3 次以上模型调用
- 一次追问：可能调 3 个工具 = 4 次模型调用

**一趟到底烧多少钱，现在没有数。** 哪天 loop 因为某个 bug 多转了两轮，成本翻倍，
你从 traces 里**看不出来**——因为它只记了"批判了一次"，没记"这次批判花了 1800 token"。

**最小形态**：`LlmClient.chat()` 里拿 `response.usage`（`prompt_tokens` / `completion_tokens`），
累加到 `AskContext` / `PlanningContext` 的 traces 上。

**什么时候做**：等真要优化成本的时候。现在做等于记一堆没人看的数。

### 3. 情节记忆

**它具体是什么**：另一张表，存「**发生过的事**」，不是「这个人什么样」。

**区别在这两句话**：

| | 回答的问题 | 例子 | 现状 |
| --- | --- | --- | --- |
| 偏好 | 他**是**谁 | 「不吃辣」「恐高」「带小孩出行」 | **第二档已落地** |
| 情节 | 上次**发生了什么** | 「上次杭州那家酒店隔音差」「上回第二天太赶」 | **没有** |

**你自己的例子**：下次再去杭州，能不能提醒他「上次那家别订了」？现在不行，没地方存。
第三档「看偏好」做完，仍然只是偏好——它解决的是**怎么看到、怎么删**，不是**存什么**。

**为什么先不做**：这是**新功能**，不是补课。真要做，得先想清楚三件事：
存什么粒度（一句话？一条结构化记录？）、什么时候取出来用（每次规划都注入？还是检索触发？）、
怎么防污染（记错了同样会跟着每一趟）。**没有第 1 条的评测集，这三件事都只能拍脑袋。**

---

### 4. 一个模型打天下

**它具体是什么**：`container.py` 里 `llm_client` 只 new 了一次，**六个地方共用同一个实例**；
模型名和温度各只有**一个**配置项。

| 位置 | 干的活 | 量 | 难度 |
| --- | --- | --- | --- |
| `PlanningDataAgent` | 取数（把三个工具调一遍） | **最大** | 最低（几乎是机械的） |
| `RequirementAnalysisService` | 需求理解（固定 schema 抽取） | 大 | 低 |
| `LlmNarrationService` | 写叙述文案 | 中 | 中 |
| `TripAdjustmentAgent` | 改方案 | 小 | 中 |
| `LlmCriticAgent` | 批判方案 | 小（但一趟转好几轮） | **高** |
| `AskAgent` | 追问（判意图、抽偏好） | 小 | **高** |

配置项（`config/settings.py:47-48`）：

```
TRAVEL_LLM_MODEL        默认 qwen-plus
TRAVEL_LLM_TEMPERATURE  默认 0.2
```

**所以现在的处境是**：档位必须按**最难的两处**（批判、追问）来选，于是量最大的两处
（取数、需求理解）在按贵模型付费。反过来选便宜的，批判和追问就变差。温度同理——
取数巴不得是 0，一个 0.2 管着全部。

**最小形态**：`LlmSettings` 加一组 fast 档（`TRAVEL_LLM_MODEL_FAST`），`Container` 里建两个 client，
按位置注入——便宜的给取数与需求理解，贵的给批判与追问。**改动很小。**

**为什么现在不做**：换完之后**没法知道质量掉了没有**。这一步正好依赖第 1 条。

## 五、本轮记账：修完了，但留了两条尾巴（2026-10-16）

重建景点库那一轮（`d186536` / `4c992b9`）修掉了 hours 空 36 条。验收时翻出来两件事，
**都是故意不修的**，记在这里免得被下一个人当成漏改、或者被"顺手修好"。

### 5.1 合并层的洞只补了一半

`build_kb.merge_skeleton` 现在按 `supplement.get(field) is not None` 判，护住了 `null`。
但 **`[]` 和 `""` 照样往下盖**——补充表 138 条**每一条**都带 `closed_days` 键，其中
**108 条写的是 `[]`**。判据不能用 falsy（票价那个 `0` 是有效值），所以只护 `null`
是这个约束下的最优解，不是疏忽。

**别再往前一步。** 实跑命中一条：`颐和园`，骨架推出 `['周一']`，被 `[]` 盖掉——
看上去像丢数据，**但这里的 `[]` 是对的**，见 5.2。

### 5.2 闭馆日会被 opentime2 里**别的主语**带跑（真 bug，在本轮上游）

高德给颐和园的 `opentime2` 是一大段，末尾写：

> 除法定节假日外，**德和园、佛香阁、博物馆、苏州街4处园中园**及……院落景点，**逢周一闭园**。

闭的是**园中园**，颐和园本身是「周一至周日 06:00-20:00」。`parse_opentime2` 从整段里
捞到「逢周一闭园」，把它算到了整个园子头上——于是骨架给出 `颐和园闭馆：周一`。

**今天看不见**，纯属被 5.1 那个洞的 `[]` 盖着。所以 5.1 和 5.2 是**耦合**的：
谁要是把 `[]` 也一并护住，这条错的闭馆日立刻浮到用户面前。

**为什么这轮不动**：`parse_opentime2` 是**运行时和离线共用**的（追问侧现查开放时间也走
它，见 `docs/ASK_LIVE_HOURS.md`），改它等于同时动两条链；而且「哪句话在说哪个主体」
不是正则能判的，得先想清楚是加分段解析、还是干脆在闭馆日上保守（判不准就不给）。

**要动它的时候，先看这一条。**
