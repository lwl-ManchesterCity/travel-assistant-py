## 一、一句话口径

**酒店和景点不能互相依赖。先把景点按位置串成一条动线，再把酒店放在动线的末站。**

现在的代码两条都想要——"景点贴酒店"＋"酒店贴景点"——所以绕一圈之后谁也站不住。

## 三、现状的五个问题

### 3.1 没有排序

`decision.attractions` 的顺序 **就是选择顺序**（`_prioritize_candidate_attractions:342`）：

```python
sorted(attractions, key=lambda a: (
    _distance_band_to_hotel(hotel, a),   # 离酒店近的档排前
    -score,                              # 同档内分数高的排前
    ticket_price,
))
```

**所以当天第一个景点＝离酒店最近的，最后一个＝离酒店最远的。**

**顺序是从酒店推出来的 → 不能反过来用它定酒店。** 这是个环。

### 3.2 已选锁死，顺序全靠分数

```python
used_attraction_names: set[str] = set()          # :106  存的是**名字**
if candidate.name in used_attraction_names: continue
```

**已选的一旦进去就永远不会被踢出来**（`_try_select_attractions:429`）。所以谁先进谁锁死，**后面的高分景点再也进不来**。

### 3.3 近邻判据会把顺路链子砍断

```python
# :1274-1280
def _is_reasonably_close(self, selected, candidate) -> bool:
    for attraction in selected:
        if distance(attraction, candidate) > 30:
            return False        # ← 跟**每一个**已选比，有一个超就拒
    return True
```

实测推演（坐标为示意）：

```
景点 (0,0) (30,0) (60,0)，起点 (-100,0)

选 (0,0)   ✓
选 (30,0)  (0,0) 到它是 30 → 不 >30 → ✓ 收下
选 (60,0)  (0,0) 到它是 60 → >30   → ✗ 拒掉
```

**但 (60,0) 距上一站 (30,0) 只有 30，`(0,0)→(30,0)→(60,0)` 是一条顺路的直线。**
判据拿"到**最老那个**的距离"，把顺路的链子从中间砍断了。

### 3.4 酒店贴中心，中心不代表任何东西

`_calculate_center` 是算术平均。对一条**有方向**的动线，平均值没有意义：

```
一天走 A→D→E，住 A 和 E 的中点 → 两头都要跑
应该住在 E —— 晚上你人在那儿
```

### 3.5 判重用 `name` 不用 `id`

景点库里有 `id`（`hz-001` 这种），规划器判重却用 `name`：

- 同名景点 → 被当成一个，第二个永远选不上
- 名字差一个括号/空格 → 被当成两个，可能同一天去两遍

## 四、新逻辑

### 4.1 分三种天

| 天的类型 | 判定 | 选景点的判据 |
| --- | --- | --- |
| **到达日** | `day_index == 0` | 以**到达口岸**为圆心，范围内取**分数最高** |
| **离开日** | 最后一天 | 在**前一晚酒店**或**离开口岸**附近取分数最高（半径圈同到达日） |
| **普通天** | 其余 | **贪心插入**（见 4.4） |

**为什么到达日/离开日不能走贪心插入**：那两天只要 1 个景点，贪心会退化成"选最近的"——而那时要的是"范围里最好的"。

```
到达日候选：A(离口岸 5km，分数 60)、B(离口岸 9km，分数 90)
  贪心 → 选 A（增量小）
  该要 → 选 B（分数高）
```

### 4.2 到达日

```
圆心 = planner_input.arrival_point     # 已有，:169 现在只用于算路线
半径 = 10km 起步
    圈内景点 < 2 个 → 放宽到 20km
    还不够         → 30km
    还不够         → 不限范围，纯按分数（回到现状行为）
取圈内**分数最高**的那个
酒店贴它（只有一个景点，等价于"贴中心"）
```

**为什么要回落**：机场都在远郊（萧山机场离西湖 25km+），**10km 圈里一个景点都没有**。到达日本来就该先进城，"离机场近"不该是那天的选景点标准。

### 4.3 离开日

```
圆心    = 两个：前一晚的酒店、离开口岸（planner_input.day_end_points，已有）
半径    = 10km 起步，与到达日**同一套回落**（圈内 < 2 个 → 20 → 30 → 不限）
命中    = 落在**任一**圆心圈内的景点（两个圈取并集）
取命中里**分数最高**的那个
酒店不变（还是前一晚那家）
```

**为什么改成"附近"而不是"绕路增量"**：绕路增量要先算两段真实里程（`酒店→景点→口岸`
减 `酒店→口岸`），里程走高德就是额外两次调用；半径圈只用已有坐标，
**跟到达日共用一套代码**，不必再维护第二套判据。

**为什么是并集、不是交集**：机场都在远郊（萧山机场离西湖 25km+），
要求一个景点同时落在酒店和口岸的 10km 内，等于要求"住机场旁边"——**一个都选不出来**。
并集两头都收：住在市区就选酒店附近的，前一天已经住到口岸附近就选口岸附近的。

**这个写法已知的粗糙处**：并集允许「酒店附近、但离口岸 40km」的景点入选，
那天会变成 `酒店 → 景点 → 40km → 口岸`。严格按顺路算，这种天该被扣掉。
先按拍板的半径圈走；真跑出这种天，再叠一道绕路增量，不提前加。

### 4.4 普通天：贪心插入

**不再用"近邻"和"总长"两个各自为政的闸门，只用一个量：插进去之后动线变长多少。**

```
起点  = 前一晚的酒店
动线  = 空
候选池 = 分数前 (target_count + 2) 名

重复 target_count 次：
    对池子里每一个还没用过的候选 c：
        算出：把 c 插到动线的最优位置，总长增加多少
    在「增量最小的那些」里挑，且要求「插完总长 ≤ 上限」
    加入（插入的位置就决定了顺序）
```

**推演**（起点 `(-100,0)`，候选 `A(0,0) B(30,0) C(60,0)`，要 2 个）：

```
第 1 步（动线为空）
   放 A → (-100,0)→(0,0)   总长 100   ← 最少
   放 B → 130
   放 C → 160
   → 选 A

第 2 步（动线 = (-100,0)→(0,0)）
   插 B：插 A 后面 → 100 + 30 = 130   增量 30   ← 最少
   插 C：插 A 后面 → 100 + 60 = 160   增量 60
   → 选 B

结果：(-100,0)→(0,0)→(30,0)，总长 130，顺序天然是 A、B
```

**这一步同时解决了三件事：**

| 现状的问题 | 贪心插入怎么解决 |
| --- | --- |
| 没有排序（3.1） | **插入位置就是顺序** |
| 已选锁死（3.2） | 每步都重新看全部候选，**后进来的可以更优** |
| 近邻砍断链子（3.3） | **不需要"近邻"这个概念**——增量小自然接得顺 |

### 4.5 选酒店（三种天统一）

```
酒店 = 贴当天动线的**末站**
```

- 到达日：只有一站，等价于现状
- 普通天：末站 = 贪心插入排出来的最后一站
- **离开日：没有酒店。** 那天你从口岸直接走了，晚上不在城里——这一格留 `None`，
  酒店钱也就不进总预算（3 天的行程只该有 2 晚）。它排在 strict 前面：
  "整趟住同一家"管的是住哪几晚，返程那天压根不是一晚。

**离开日的一个例外**：用户为那天**亲口指了**住宿位置（`dayHotelAnchors` 里有这一天）时听人的，
照旧从那天的候选池里挑——那句话是他说的，不能静默吞掉。
整趟那个锚点（`hotelAnchor`）不算：它在第 1 天已经生效过，不用再管这天。

**这天选景点的圆心**因此是「前一晚那家酒店」＋「口岸」——返程日自己没有住宿，
圆心退回你早上醒来的地方。

**为什么敢去掉"景点贴酒店"**：那一条当初（2026-10-09）是为了"别让景点离酒店太远"。**酒店放到末站之后，它自动就满足了**——景点串成一条线走到酒店。

### 4.6 为什么候选池是 `target_count + 2`

```
池子 = target_count      → 没得挑，贪心退化成"照单全收"
池子 = target_count + 2  → 有得挑，分数也不会太差（要 2 个 → 4 选 2，6 种组合）
池子 = 全部（现状）       → 挑得出顺路的，但**很冷门的景点会因为"顺路"被选进来**
```

## 五、参数表

| 项 | 值 | 依据 |
| --- | --- | --- |
| 候选池 | `target_count + 2` | 已拍板 |
| 到达日半径 | 10km，不足 2 个则 20 / 30 / 不限 | 已拍板（10km 对高铁站够，机场靠回落兜） |
| 离开日半径 | **同到达日**（10 / 20 / 30 / 不限） | 已拍板；原「绕路增量 10km」作废 |
| 当天总长上限 | **待定**，建议 25km | 见下 |
| 近邻 | **取消** | 被绕路增量替掉 |
| 判重 | `name` → **`id`** | **已做**，见下 |

**`name` → `id` 怎么做的**（比预想的小得多）：

1. `Attraction` 加一格 `id`（`models/attraction.py`）。
2. `AmapAttractionClient._to_attraction` 把 `poi.get("id")` 填进去——**这个 id 本来就在手上**
   （`_contains_poi_by_id` 一直拿它给 POI 去重），只是以前没往上传。**取数链路一行没动。**
3. 规划器加 `_attraction_key()`：有 id 用 id，没有才退回名字。`used_attraction_names`
   随之改名 `used_attraction_keys`，`_contains_attraction` 也改成比 key。

**前端不用动**：`Attraction` 是 `CamelModel`，多一个 `id` 字段是加法，页面上的 JS 只读它要的那几个
（`name`／`address`／`location`…），多出来的字段直接忽略——不存在"契约破坏"。

**本地知识库那个源造不出 id**（`clients/knowledge_base.py` 是写死的构造），所以它那批 `id` 是 `None`，
判重退回比名字——与加这一格之前完全一致。同一次规划里两种键会混着用，这是有意的。

**总长上限 25km 的由来**——用用户自己那份方案里的真实数据当锚：

```
方案里第二天：93 分钟通勤 / 31.4 公里 / 4 段路线
模型自己判它「显得赶」
                ↓ 约 3 分钟 / 公里
25 km → 约 75 分钟（可接受）；31.4 km → 93 分钟（赶）
```

1. 普通天排出的动线，**总长 ≤ 上限**；排不出时上限**逐级放宽**到 50（见七之二第 2 条）。
2. 普通天**不出现**"两站之间超过 30km 却仍被排进同一天"的情况（3.3 那个反例不再复现）。

7. 到达日/离开日**只排 1 个**景点。

## 七、还没确认的事

1. **到现在也没跑过一次真实的 `/plan`。** 3.1~3.5 那五条是读代码读出来的，实现和判据走的都是
   构造用例（`tests/test_planner_agent.py`）。**真跑一遍仍然要做**——尤其看真实的
   `_sanitize_attractions` 会砍掉多少候选（它按 35km 聚类，砍完池子可能不够排）。
2. **总长上限 25km 只有一个锚点**（用户那份方案的 31.4km）。样本太少，跑真数据后可能要调。
3. **离开日的"或"写成了并集**（酒店圈 ∪ 口岸圈）。并集放过「酒店附近、离口岸 40km」这种天；
   要不要再叠一道绕路增量，等真实反例再定，不提前加。
4. **里程走的是直线（haversine），不是高德里程。** `_calculate_distance_km` 一直如此，
   上限 25km 也是按这个尺子定的。真实道路里程通常是直线的 1.2~1.4 倍，
   所以"25"对应的高德里程可能到 30~35 公里——**要调就调这一个数**。

## 七之二、实现时新冒出来、原文没写的三件事

1. ~~返程那天沿用前一晚的酒店~~ **已推翻**：返程那天现在没有酒店（见 4.5）。
   连带的效果是总预算少算一晚——3 天的行程本来就只有 2 晚，这比原来更对。
2. **上限排不出时是"逐级放宽"，不是"硬塞一个"。** 梯子 `(25, 50)`：25 排不出就往 50 放。
   为什么要放宽而不是直接给一个最近的——**放宽之后还能多接一站**：
   `起点 →33km→ A →3km→ B` 在 25 这一级两个都进不来，放到 50 就 A、B 一起进来。
   放到 50 就停：再宽下去贪心会一路填满，排出两站相隔 70 公里的天，跟"宁可少排也不要赶"打架。

   **放到 50 还是空**（候选全被用过、或根本没有候选）才退回"只给离起点最近的一个"——
   一个都不能少，`_build_meals`／`_build_description` 拿 `attractions[0]`／`[-1]` 当锚。
   这一条会**真的超上限**（构造用例里排过 67 公里的天），靠 ReflectionAgent 的
   "优先压缩通勤，超出约 N 分钟"写进备注，不静默。
3. **插入位置并列时取靠后的那个**（`<=` 而不是 `<`）。两条一样长就按"今天新加的一站排在最后"，
   否则同一批景点会因为浮点次序不同，一会儿插队首一会儿插队尾。
