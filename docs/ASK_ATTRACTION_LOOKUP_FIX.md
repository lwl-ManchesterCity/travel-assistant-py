# 追问侧「问一个具体景点」查不到 —— 修法

> 2026-10-13。真实运行暴露，非推测。**只动提示词与工具签名，不动检索算法、不动阈值。**

---

## 一、现象

广州方案下追问，两条问法结果相反：

| 追问 | 结果 |
|---|---|
| 广州塔门票多少钱 | ✅ 答出 150 元 + 出处 |
| 陈家祠周一闭馆吗 | ❌ 「本地景点库里没有检索到『陈家祠』」 |

**但陈家祠就在库里**：

```
陈家祠堂   票=10   hours='09:00-18:00'   closed=['周二']   tags=[室内, 拍照]
```

---

## 二、根因：两处，各自独立

### 2.1 提示词缺第三种问法（已修）

`ask_agent.py` 规则 11 原来只写了两种问法：

```
问方案里已有的那个景点（要门票吗、几点关门）→ get_attraction_detail
问有什么符合条件的（下雨天去哪、有什么免费的）→ search_attractions_by_tag
```

「广州塔门票多少钱」两条都不沾：它问的是**一个具体景点**，但不是"筛选"。规则里明写
「**几点关门**」归 `get_attraction_detail`，模型于是走那条，撞上「方案里没有这个景点」，停。

配套还有两处把话说死了：

- `get_attraction_detail` 的说明：「方案里没有这个名字时会回可选景点清单，**不会去联网查**」
  —— 只说了"到此为止"，没说"改走哪条"。
- `search_attractions_by_tag` 的说明：「按标签**筛出一批候选景点**」—— 是翻目录的口吻，
  读不出"也能按名字查某一个"。

**这一处已改**（2026-10-13）：规则 11 补上第三种问法；两处工具说明互相指路。
改完广州塔立即可答 —— 证明这一处判断正确。

### 2.2 检索词用整句，撞上阈值（**未修，本文档要解决的**）

改完提示词后，模型**确实去查库了**，但库里没查到。原因在检索词：

```python
# ask_tools.py，search_attractions_by_tag 内
rows = search_kb_attractions(city=city, tags=picked or None,
                             query=context.question)      # ← 用户原话整句
```

而 `DEFAULT_MIN_SCORE = 0.545` 会把这句整句判为"不够像"。实测（本机，四城全库）：

```
陈家祠堂 （光名字）        0.585   ✅
陈家祠堂 门票多少钱         0.569   ✅
陈家祠堂 周一闭馆吗         <0.545  ❌
```

**同一个库、同一个景点，只是问句多了五个字，就掉到线下。**

全库扫描（138 条 × 4 种问法，`min_score` 取默认值）：

| 问法 | 完全查不到 |
|---|---|
| 光名字 | 0 / 138 |
| 门票多少钱 | 0 / 138 |
| 几点关门 | **11 / 138** |
| 周一闭馆吗 | **10 / 138**（另 2 条掉出前 3） |

掉线名单含 **外滩、景山公园、玉渊潭公园、上海田子坊、六和塔、陈家祠堂、帽峰山森林公园**等。

**问句越长、名字占比越低，越容易掉线。**

### 2.3 为什么不能靠降阈值

`retrieve.py` 顶部注释记着标定过程（2026-10-11，12 条问句、60 个分数）：

```
域外问句（修手机/考驾照/海底捞）  top1 最高 0.537
域内问句（下雨天/免费景点/爬山）  top1 最低 0.554
```

**样本只有 12 条，全是"泛筛选"类型，没覆盖"具体景点"这种问句** —— 0.545 被派去做了一件
从没标定过的事。但降阈值不是解法，注释里已经写明：

> 这条限制的解法是补数据 + 提示词护栏，**不是调这个数**。

实测降阈值的代价：0.545 → 0.45 虽然让"查不到"归零，但**放开了"问无关问题也召回景点"**这个口子
—— 那正是 0.545 存在的理由。且这只是把线往下挪，遇到更长的问题还会再撞。

### 2.4 这违反了本模块自己定的口径

`retrieve.py` 第一句：

> 口径只有一句：**能用确定条件筛的，绝不交给向量。**

**景点名是最确定的条件，比 tags 还确定**，却没被当条件用，而是丢进整句里稀释掉了。

注意现存的对比：「杭州下雨天去哪」能稳过，是因为模型抽出了 tag `室内`，走**硬筛**那条路，
且 `apply_threshold = not tags` 免掉了阈值。**同一个坑 2026-10-11 已经踩过一次**
（注释里那条「灵隐寺相似度 0.5399 被 0.545 丢掉」），当时只补了带 tags 那半条路，
纯向量这半条原样留着。今天撞的就是它。

---

## 三、改法：把景点名补成一个"确定条件"

> **这不是新机制，是把既有模式搬到缺的那条链上。** 项目里已有"从用户输入抽景点名"的先例
> ——`pinHints`（规则 7/8）：模型抽出 `["广州塔"]` → 写进 `request.day_attraction_pins`
> （`trip_plan_request.py:38`）→ 规划器按天取用（`planner_agent.py:319`）。
> **它只接在"改方案"那条链（need_change）上，答疑链（answer）没有对应的一格。**
>
> 证据是提示词自身的缺口：规则 8 已经写明「**「方案里查不到这个景点」不是拒绝的理由**」，
> 但这句话只对 need_change 说，规则 11 里没有对应的表述。**同一个道理，一半写了、一半没写。**

### 3.0 链路对照（改前 / 改后）

**改前**（陈家祠挂掉的这条）：

```
① 前端发「陈家祠周一闭馆吗」+ 整份方案 → POST /api/trips/ask
② 模型判意图 → 认定"问一个具体景点" → 决定调 search_attractions_by_tag
③ 工具内部：city = 方案城市（广州）
            query = context.question = "陈家祠周一闭馆吗"      ← 整句
④ retrieve.py：where={"city":"广州"} 硬筛出 32 条
               在这 32 条里算相似度 → 整句最高分 < 0.545 → 全丢 → 返回 []
⑤ 工具回模型「没有命中的景点」
⑥ 模型照实说「库里没查到陈家祠」
```

**改后**（只有第 ③ 步变）：

```
③ 工具内部：city            = 广州
            attraction_name = "陈家祠"                    ← 模型填的（新加的一格）
            query = attraction_name or 整句 = "陈家祠"     ← 检索词短了
④ where 仍是硬筛那 32 条；相似度 "陈家祠" = 0.575 > 0.545 → 命中
⑤ 工具回模型完整那条：票价 10 / 09:00-18:00 / closed_days=['周二'] / 出处
⑥ 模型读到 ['周二'] → 答「不闭，是周二闭馆」
```

**关键差别只有"送去检索的那个词"**：整句 → 0.53 丢；纯名字 → 0.575 中。

**为什么不算改算法**：`search_attractions` 函数一字不动、阈值 0.545 不动、城市与 tags 两条硬筛路
不动 —— **只换检索词**。

**模型怎么知道要填**：规则 11 补一句「问具体景点时把景点名填进 `attraction_name`」。模型本来就知道
用户在问哪个景点，只是原来没有地方放这个名字（14 词的 tags 词表装不下）。

**不填会怎样**：`attraction_name or context.question` 原样退回今天的整句 —— **最坏情况 = 今天，不会更差。**

### 3.1 工具加一个参数（`travel_assistant/agent/ask_tools.py`）

```python
def search_attractions_by_tag(tags: list[str] | None = None,
                              attraction_name: str = "") -> str:
```

工具说明补一句：问具体景点时把景点名填进 `attraction_name`。

### 3.2 检索词名字优先（同一个函数内，一行）

```python
rows = search_kb_attractions(city=city, tags=picked or None,
                             query=attraction_name or context.question)
```

**没填就退回现状，不会更差。**

### 3.3 提示词（`travel_assistant/agent/ask_agent.py`）

规则 11 第三种问法里补：把景点名填进 `attraction_name`（原来写的是"不用传 tags"）。

## 四、判据（怎么算修好了）

1. **数据层**：`search_attractions(city, query=景点名)` 全库 138 条**零失败**（现成基线，已实测）。
2. **端到端**：广州方案下追问「陈家祠周一闭馆吗」，答出**周二闭馆**并带出处。
3. **不回归**：追问「杭州下雨天去哪」仍走 tags 硬筛那条路，答案不变。
4. **不回归**：问一个库里真没有的景点（如「广州塔旋转餐厅」），仍如实答查不到 —— 不许硬凑。
5. `pytest` 全绿。
6. 现有判据 `tests/test_ask_agent.py::test_shouldPutVocabularyAndScopeIntoTheToolDescription`
   仍过（工具说明里的词表与城市范围不能被改坏）。

---

## 五、明确不做

- **不降 `DEFAULT_MIN_SCORE`。** 理由见 2.3，且与 `retrieve.py` 注释里的既有决定冲突。
- **不改 `_where` 的筛选语义、不改 tags 那条路。**
- **不引入联网兜底。** 联网那个工具（`search_attractions`，走高德）返回的只有名字/类别/地址，
  **没有票价、开放时间、闭馆日**（`ask_tools.py:95-100`）。这类问题本地库是唯一来源，
  查不到就是查不到 —— 这一点要在验收时确认模型照实说，而不是拿估算票价顶替。

### 6.1 顺带发现：答疑类问句常常不穿 JSON 外壳（**与本次改动无关，未修**）

`AskAgent` 的轨迹里频繁出现 `fallback`，原因是**模型最后一轮直接吐了答案文本、没输出规则 9 约定的
JSON**，于是 `_parse_final` 回落成 `answer`（设计里的安全方向，答案本身是对的）。

实测 7 次：答疑类 4/4 回落，改方案类 0/3 回落。**方向是安全的**（回落默认 `answer`，而这 4 轮本来就
该是 `answer`；真正危险的反方向——把改方案判成答疑——3 次都没发生）。
判断与本次改动无关的依据：「广州有什么免费景点」也回落，而那条根本不碰新加的 `attraction_name`。
**本次未处理**，若要收敛应单独议（改规则 9 的措辞，或在 `_parse_final` 里认纯文本）。

## 七、遗留

- 库里 51 条有 `aliases`，但**没有覆盖"陈家祠 → 陈家祠堂"这类简称**。本次改法靠向量按名字命中，
  能覆盖简称（实测「陈家祠」单独检索 0.575 过线）。若将来出现向量也命不中的别名，再补 aliases。
- `duration_min` 等既有偏差不在本次范围。
- **规则 11 第一条的划线是错的**：它把「几点关门」划给 `get_attraction_detail`，但那个工具读的是
  方案里的字段，**根本没有开放时间/闭馆日**（方案里只有"门票按类别估算"）。这次模型自己绕过去了
  （实测「越秀公园几点关门」改走了本地库），但规则本身还在误导。要改就把「几点关门」从第一条
  挪到第三条，与「门票多少钱」并列。
- 答疑类问句的 JSON 回落见 §6.1，未处理。
