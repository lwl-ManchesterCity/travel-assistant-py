# 多轮追问：上下文链路与短期记忆

> 2026-10-14。**本文已落地**（落地记录见 §七）。
> 上游：`docs/ASK_AGENT_DESIGN.md`（追问 agent 本体）、`docs/ASSISTANT_CHAT_DESIGN.md`（助手页 UI）、
> `docs/ASK_SCOPE_OPENING.md`（开放范围，与本文件并行、互不依赖）。
>
> 起因是用户发现：「我现在也能多轮呀，不过现在的多轮不会添加到上下文去」——
> 界面上的多轮早就有，模型眼里的多轮一个都没有。本文补的就是后者。

## 一、现状（对代码实测，非推测）

| 位置 | 现在是 |
|---|---|
| 后端 `agent/ask_agent.py:148` | `invoke({"messages": [HumanMessage(content=request.question)]})`——**永远一个元素的列表** |
| 前端 `static/js/app.js:1122` | 请求体只有 `question` / `tripPlan` / `request`，**没有历史** |
| 前端消息 | 只以 DOM 节点存在，**没有数组**（grep `let *(messages\|history) = [` = 0 处） |
| 服务端 | **无任何会话状态**（无 session / redis / sqlite / checkpointer） |

所以每一轮都是一次全新 `invoke`，上一轮说过什么模型完全不知道。

**但要说清一点**：不是"模型什么上下文都没有"——**方案一直在它手里**（七个工具读 `tripPlan`），
只是**对话上下文**没有。所以：

```
问「西溪湿地要门票吗？」   → 答得出（方案里有这个景点）
问「那它开放时间呢？」      → 「那」「它」没有指代对象，答不出
```

## 二、上下文链路：什么进 prompt，什么不进

这张表是本文最容易记错的地方，先钉死（数字为 2026-10-14 实测/粗估，中文按 1 token ≈ 1.6 字）：

| 东西 | 存浏览器 | 每轮请求体传 | **进模型 prompt** | 量级 |
|---|---|---|---|---|
| 系统提示词 | ❌ 写死在代码 | ❌ | ✅ 服务端每次自己加 | ≈ 1294 token |
| 工具定义 | ❌ 写死在代码 | ❌ | ✅ 同上 | ≈ 1142 token |
| **方案 `tripPlan`** | ✅ | ✅ | ❌ **只在模型调工具时读到摘要** | ≈ 7329 token（传但**不进**） |
| **原始请求 `request`** | ✅ | ✅ | ❌ 同上 | ≈ 124 token（传但**不进**） |
| 历史对话（本文新增） | ✅ | ✅ | ✅ | ≈ 28 token/轮 |
| 当前这句 | — | ✅ | ✅ | — |
| **工具返回值** | ❌ | ❌ | ✅ 模型调了才进 | 一次查库 ≈ 129 token |

### 2.1 先分清三个动作：「短期记忆」是三层漏斗

这一条最容易混，单独说。**「存」「发」「进 prompt」是三件事**：

```
① 存              ② 发               ③ 进 prompt
sessionStorage  →  请求体         →  模型的 messages 列表

三样都进 ① ──┬─ 对话      → history 字段   → ✅ 进
             ├─ tripPlan  → tripPlan 字段  → ❌ 不进
             └─ request   → request 字段   → ❌ 不进
```

**「短期记忆」= 这次会话存下来的东西（三样）**，
它**不等于**"发给模型的东西"，更**不等于**"进 prompt 的东西"。

常见两种误读：

- ❌「只把对话存进短期记忆」——那刷新后方案没了，对话留着也没用（追问必带 `tripPlan`，见 §六第 1 条）
- ❌「把整个短期记忆都塞给模型」——方案 7.3k token 全进 prompt，又贵又没必要

✅ 正确做法：**三样都存；发的时候拆成两个字段**，只有对话那一路进 prompt。

### 2.2 一次追问是**循环**，不是一次调用

表里「工具返回值 → 进模型 prompt」那行容易卡住：既然顺序是"拼装上下文 → 调 LLM → 模型调工具"，
那工具结果怎么会在 prompt 里？

因为**一次追问里 LLM 被调用好几次**：

```
用户问「灵隐寺要门票吗？」

① 拼装 messages ──→ 调 LLM   【第 1 次】
     messages = [系统提示词, 工具定义, Human「灵隐寺要门票吗？」]
   模型回：我要调 search_attractions_by_tag(attraction_name='灵隐寺')

② 执行工具
   返回「命中 1 条：灵隐寺｜门票 30 元｜开放 07:30-17:30…」

③ 工具结果追加进 messages ──→ 再调 LLM   【第 2 次】
     messages = [系统提示词, 工具定义, Human「…」,
                 AI(我要调工具),
                 Tool(命中 1 条：…)    ← 工具结果在这里进 prompt
   模型回：{"intent":"answer","answer":"灵隐寺门票 30 元…"}

④ 模型没再说要调工具 → 结束
```

「拼装上下文 → 调 LLM」这个动作**一轮里发生好几次**（`create_agent` 的循环）。
**工具返回值进的是第 2 次及以后的 prompt，不是第 1 次。**

这也是前端 SSE 里工具条目**一条条冒出来**的原因——每一条就是循环里转的一圈。

**与 §3.3 的关系**：工具结果**本轮之内必须进 prompt**（不然模型看不见工具返回了什么，没法答），
**只是不跨轮带**——下一轮的第 1 次调用里没有它。

### 2.3 两个关键点

1. **方案和请求是"传了但不进 prompt"**。它们存在 `AskContext` 里，模型要用时**调工具去读**
   （`get_plan_overview` 返回的是每天一行的摘要，不是整份 JSON）。
   **七个工具存在的意义就是这个**——让大数据不必躺在上下文里。这也是大方案撑不爆上下文的原因。
2. **固定开销（提示词 + 工具定义 ≈ 2436 token）比对话历史大一个数量级**，
   而它跟记忆无关，今天就已经在付了。

## 三、历史怎么带

### 3.1 存在哪 → `sessionStorage`

用户定的分层：

| 存什么 | 存哪 | 对应 |
|---|---|---|
| 方案 + 对话 | **`sessionStorage`** | ① 短期记忆（这次会话） |
| 偏好 | `localStorage` | ③ 长期偏好记忆（**本次不做**，见 §六） |

**为什么短期用 `sessionStorage`**：助手的定位是"方案生成之后的下一轮"（见 `ASK_SCOPE_OPENING.md` §三），
**关掉标签页 = 方案没了 = 对话也没用了**，持久化对话本来就没意义。
它还顺带解决两件事：不留陈旧数据（不会一打开就看到三天前放弃的方案）、多标签页不打架。

**触发换 `localStorage` 的条件**：把助手往前推（能脱离方案单独用、或从首页直接进）的那天。
到那时"关掉标签页就得重新规划"这个前提不成立了，才需要持久化。**换起来只是改一个词。**

**注意**：`sessionStorage` 名义上"关标签页就清"，但浏览器**"恢复上次会话"**
（Chrome 关掉整个浏览器再打开、选继续上次的标签页）时**通常会把 sessionStorage 一起恢复**，
各家行为不一致。所以别把它当"一定会被清干净"的保证——要保证就在方案生成成功时显式 `clear()`。

### 3.2 带什么内容 → 存**解析后的 `answer`**，不存模型原始输出

模型的原始输出是规则 9 约定的 JSON 信封（`{"intent":"answer","answer":"…"}`）。
存原文等于每轮把脚手架喂回模型，而且是在教它"我上次就是这么答的"。

### 3.3 **不带工具结果**——这是本设计里最反直觉的一条

一轮追问内部其实是好几条消息：

```
HumanMessage   「西溪湿地要门票吗？」
AIMessage      (tool_calls: search_attractions_by_tag)
ToolMessage    「杭州本地景点库命中 2 条：西溪国家湿地公园｜门票 80 元｜开放 08:00-17:30…」  ← 工具结果
AIMessage      「西溪湿地的门票是估算 80 元…」                                          ← 存这条
```

**下一轮只带 Human 和最后的 AI，中间的 Tool 全部丢掉。** 三个理由：

**① 体积差一个数量级。** 实测：

```
一次查库（命中 2 条） ≈ 129 token
命中 10 条（_LIST_LIMIT）≈ 650 token
一轮问答            ≈  28 token
```

一轮追问里模型可能调两三次工具，那就是几百到一千多 token——
而我们不带的那 8 条历史加起来才 220。

**② 它会拆掉规则 2 的闸门。** 规则 2 现在管的是"每个数字都要能在**本轮**工具返回值里找到原文"。
历史里带上旧工具结果，模型就能拿十轮前的原文说事，而那份数据可能早就过期了
（尤其 `/adjust` 改了方案之后）。**"本轮"这个限定是故意留的闸门。**

**③ 不带也够用。** 规则 2 保证了答案里的数字都有工具原文，所以事实**已经沉淀在模型自己的回答文本里**：

```
历史：  「西溪湿地门票 80 元，开放 07:30-17:30」   ← 模型自己上一句说的
你问：  「那它几点关门？」
模型：  知道"它"= 西溪湿地 → 重新调工具查一次 → 用新数据答
```

**指代接上了，数字还是新鲜的**——而且比复用旧结果更好（票价、天气、路线、酒店都会变，
七个工具返回的全是这类"一次性快照"）。

### 3.4 窗口 → 最近 6 轮 + 8000 字符兜底

先看数字，**这不是"怕撑爆"，是实际上撞不到**：

```
一轮问答    ≈ 28 token
一百轮      ≈ 2800 token   ← 聊一百轮，才刚赶上系统提示词那个量级
固定开销    ≈ 2436 token   ← 每轮都在，与聊多久无关
```

所以做窗口是为了另外三件事：**质量**（50 轮前的东西只会稀释注意力）、**成本**、**延迟**。

- 主判据：**最近 6 轮**（12 条消息）——追问里的"那""它"基本只指上一两句
- 兜底：**8000 字符**——规则 10 要求答案 ≤3 句，但模型不一定守

**两个实现细节**：

1. **成对丢。** Human 和它对应的 AI 答案一起丢，只丢一条会出现"AI 答了一句用户没问过的话"。
2. **前后端都截。** 前端截是别发没用的东西；**后端也必须截**——不能信任客户端，
   否则构造一个一万轮的历史就能打爆服务。

### 3.5 为什么**不做**滚动摘要（近处保原文、远处压摘要）

用户提过这个做法（分层记忆），方法本身是对的，但在这里算下来不划算：

```
10 轮原文          ≈ 280 token
概括成一段摘要      ≈ 200 token   ← 中文摘要压不了太多
每次省下           ≈  80 token
─────────────────────────────
生成这段摘要要      ≈ 480 token（一次额外的 LLM 调用）
```

**省下的（80）比生成本身的（480）还少**，而且历史变长还得重摘。

更要紧的是**压掉的正好是追问要用的**：

```
原文：  「西溪湿地门票 80 元，开放 07:30-17:30」
摘要后：「讨论了几个景点的门票和开放时间」
              ↓
下一句「那它几点关门？」 → 接不上了
```

而且摘要也是模型写的，会漏会错，**错的部分还会被当成事实一路带下去**。

**什么时候该上它**：历史本身很大的时候（历史里带着工具返回的原文档、贴论文/合同的文档问答）。
我们刻意只带文本对话、不带工具消息（§3.3），那个决定本身就把单轮压得很小了。

**两条路不冲突**：窗口是"先做对，最简单"；哪天发现真不够用了，
再在窗口上面套一层摘要，前面的代码不用推翻。

## 四、提示词的改动：**只有一句**

**规则 2 的「本轮」一个字都不要改。** 一度想改成「本会话」，那是**错的**——
它现在是防止把历史里的旧数字当事实用的关键闸门（§3.3 理由②），改了反而放开。

只需要补一句：

> 历史用来理解用户在指谁、指哪一天，**不是事实来源**。

## 五、与 `/adjust` 的关系 → **不切，全给模型**

改完方案后，历史里那些回答说的是**旧方案**。多轮之前它们对模型不可见所以无害，
多轮之后模型会读到——这是这次改动带来的**唯一新增风险**。

一度设计过"插一条分隔线，只把分隔线之后的消息发给模型"。**用户否掉了，理由更好**：
切了之后「刚才那个呢」就接不上了。

**改为靠规则 2 挡**：模型看到历史里的「西溪湿地门票 80」，知道"那"指它，
然后**重新调工具**拿到新数字再答。旧数字不会直接被转述，因为规则 2 要求每个数字都有**本轮**工具原文。

**接受的代价**：如果某个数字只出现在历史里、本轮没重查，模型应当说"我需要重新确认一下"。
规则 2 已经这么要求了，但**模型会不会守是验收要盯的**（见 §七 判据 5）。

## 六、明确不做

1. **不做登录、不做落库。** 方案与对话只活在浏览器里，刷新页面在（`sessionStorage`），
   关标签页失效——与今天一致。
2. **不做长期偏好（③）的实现。** 那需要 LLM 抽取 + "看得见、删得掉"的管理界面，
   是独立的一档。用户明确"后面我会做规范"。
3. **不把工具结果放进历史**（§3.3）。
4. **不做滚动摘要**（§3.5）。
5. **不动 `/api/trips/ask` 的行为。** `history` 是**可选**字段，不传就是今天的样子。

**前端另验的几条**（`/tmp/multiturn_frontend_probe.py`，13 条全过）：

- 第一问的请求体 `history` 为空；第二问带上完整的一问一答，且**当前这句不在里面**（后端自己拼）
- `history` 里存的是**解析后的答案**，不含 `{"intent":...}` 信封
- sessionStorage 里方案、原始请求、对话三样都在
- **刷新后**：停在方案页、首页藏起、对话 4 条气泡都在、表单回填目的地与预算、接着问带满 4 条历史
- 重新规划后对话清空

## 八、落地时踩到的坑（记一笔）

- **`restoreSession()` 必须放在整个脚本的最末尾**。放在函数定义旁边会踩暂时性死区：
  它要走到 `renderResult`，而那条路上用了 `app.js:1823` 的 `const lineColor`——
  那时还没初始化，抛 `Cannot access 'lineColor' before initialization`，
  表现是**刷新后停在首页、方案压根没渲染出来**。
  文件开头那几行初始化之所以没事，是因为它们不走渲染。
- **末尾孤立的 Human 要先摘掉再配对**。直接从末尾往回配的话，第一步就配不上，
  `break` 出去会把**整段**历史一起丢掉——不是"丢掉那一条"。
- **前端只记成功的轮次**，而且一问一答一起记。只记 Human 不记 AI 更糟：
  末尾那条配不上，同样会把整段历史丢掉。

## 九、遗留

> **长期记忆（用户偏好）已独立成文**：`docs/ASK_LONGTERM_MEMORY.md`（决策已定，设计待展开）。
> 下面那条「长期偏好设计草稿」以那份文档为准。


- **`AskRequest` 里已经有个没人用的 `thread_id`**（`models/ask_request.py:24`）。
  将来若要走服务端会话（checkpointer），它是现成的挂点。**本次不用。**
- **不需要 checkpointer。** 实测：`create_agent(model, tools=[]).invoke({"messages":[三条]})` 成功，
  模型收到 system + 三轮；`checkpointer` 参数默认就是 `None`，它只在**服务端要自己记住会话**时才需要。
  前端本来就握着屏幕上的消息，一起发过去即可——**零新依赖**，`requirements.txt` 保持 10 行。
- **长期偏好（③）的设计草稿**（用户后续自行规范，此处只记已聊定的）：
  - 来源是**从对话里推断**（「有没有不用爬山的」→ 记下"不喜欢爬山"），不是让用户填表
  - 注入位置是**系统提示词**，不是历史——偏好必须每次都生效，不能让模型自己决定读不读
  - **表单优先于长期偏好**（用户这次明确说的，比历史推断更权威）
  - 抽取要防**过度推断**：只记明确说的、**存了必须看得见删得掉**
    （原写的「重复出现才升级为长期」已作废——与 `ASK_LONGTERM_MEMORY.md` §1.2 冲突。
    那条守则说「我不能吃辣」这类**首次提及就要存**，门槛在"是这个人还是这一趟"，不在"说几次"。）
  - 抽取时机不做成实时（每轮抽会让一次追问变两次 LLM 调用），等落库时用异步任务批量跑
