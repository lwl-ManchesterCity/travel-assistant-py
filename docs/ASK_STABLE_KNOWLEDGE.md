# 景点问题分两条路：**会变的查库，不会变的自己答**

> 2026-10-15。上游：`docs/ASK_LIVE_HOURS.md`（姊妹篇，**设计已写、未实现**）、
> `docs/ASK_ATTRACTION_LOOKUP_FIX.md`、`docs/ASK_SCOPE_OPENING.md` §2.2（规则 11 的来源）。
> **本文是待审的设计，还没动代码。**

---

## 一、这件事是什么

**规则 11 现在把「某个景点的客观信息」一股脑推给本地库，但其中「不会变的那半」本来就该模型自己答。**

```
用户：广州塔有什么看点
现在：search_attractions_by_tag(景点名=广州塔) → 本地库没收 → 「查不到」     ❌
应该：模型直接答（看点、历史、适合谁——几十年不变，它答得比库好）
```

触发这次讨论的原话是「向量库里没有就发高德 API，API 也拿不到就让 LLM 自己思考回答，
再让它自己判断合不合理」。**其中「自己判断合不合理」那一环不成立**（§三 末），
所以本文只做「按类型分路」，不做「让模型自查事实」。

## 三、两种问题

| | **会变的**（事实型） | **不会变的**（常识型） |
|---|---|---|
| 例子 | 门票多少钱、几点关门、周一闭馆吗、要预约吗、电话 | 有什么看点、为什么有名、适合带小孩吗、多高、哪年建的 |
| **判据** | **换一年再问，答案不一样** | **十年后问，答案一样** |
| 走哪 | **查库**（本地库 → 联网，见 `ASK_LIVE_HOURS`） | **模型直接答，不查** |
| 查不到 | **照实说查不到** | 不适用（压根不查） |

**判据是「换一年问，答案会不会变」，不是「是数字还是文字」。**
「广州塔多高」（600 米）是数字但不变 → 常识型；「门票多少钱」是数字会变 → 事实型。

### 为什么不能让模型兜事实型

> **同一个模型、同一份权重，判断不出自己记错了。**

`LlmCriticAgent` 那套能批判，是因为它批的是**方案内部的逻辑**（时间够不够、路线顺不顺），
那是**内部一致性**，模型看得出来。「票价是不是 60」是**外部事实**，它手里没有第二个来源对照。

规则判断也一样：只能做形状检查（数字范围、有没有出处），**判不出真假**。
而「形状对」恰恰是幻觉的特征——**编出来的票价往往比真话还整齐**。

**判断「这题是事实型还是常识型」模型能做**（它判的是**问题**）；
**判断「我答的票价对不对」它不能做**（它要判的是**答案**）。让考生自己选题可以，自己批卷不行。

## 四、设计

### 4.1 规则 11 怎么改

现在那条把「某个景点的客观信息」整体推给本地库。拆成两条：

- **会变的** → 照旧 `search_attractions_by_tag`，查不到照实说。**这条不动。**
- **不会变的** → **直接答，不查库。**（这是本文唯一新增的行为）

### 4.2 常识型的回答里**不许夹会变的数字**（本档唯一的硬约束）

> 讲看点的时候想提票价，**不许凭记忆说**——要么先去查（转走事实型那条路），
> 要么就不提。

**理由：幻觉最像真的地方就是数字。**「广州塔门票 150 元」和「广州塔高 600 米」在用户眼里
长得一模一样，但一个可能是三年前的，一个永远是准的。

**所以：不能因为"这题归常识型"就放开了让它报数字。** 题的类型，不等于答案里可以出现什么。

### 4.3 措辞：不许装成查来的

答常识型时**不许用「据资料显示」「查询到」这类措辞**。

理由：那些词暗示了一个**来源**，而那个来源不存在。同一次对话里前面刚查过库，
这里顺口说「资料显示」——**用户没法分辨哪一句是查的、哪一句是它自己说的**。

### 4.4 不加标注

**不加「以下不是实时数据」那种提示行。**

按 §4.2，常识型的答案里**压根不会出现会变的东西**，那句标注就没有指代物。
`ASK_LONGTERM_MEMORY.md` §2.1.7 的教训：**说明那行不写废话。**

### 4.5 工具那侧**一个字不动**

`search_attractions_by_tag` 不改。改的是**规则**（模型什么时候用它），不是工具。

这条让本档的爆炸半径很小：**只有提示词一处改**，没有新代码路径、没有新表、没有新接口。

## 五、判据（怎么算改好了）

| # | 判据 | 怎么测 |
|---|---|---|
| 1 | **常识型答得出** | 问「广州塔有什么看点」→ 有实质回答，**不是**「查不到」 |
| 2 | **事实型照旧** | 问「广州塔门票多少钱」→ 本地库没有 → **仍然说查不到**，不许编一个数 |
| 3 | **不许夹数字** | 问「陈家祠有什么看点」→ 回答里**不报**票价 / 开放时间的**值**（提到词不算） |
| 4 | **不装来源** | 常识型回答里没有「资料显示」「查询到」 |
| 5 | 不回归 | `pytest` 全绿；`/tmp/preference_probe.py` 等探针全过 |

**判据 2 是反向的那条，也是最重要的一条。** 改完之后最容易出的错，是模型学会了
「可以自己答」，然后把票价也一起编了——那正是本文开头要躲开的东西。

判据 3 是防「一半对一半错」：题归常识型，但答案里顺手报了个票价，比整题答错更难发现。

## 六、明确不做

1. **不接高德那一层**——那是 `ASK_LIVE_HOURS.md` 的事，别在这里顺手做。
2. **不给常识型加检索**：本地库、向量都不用。它答的就是模型自己的知识。
3. **不加标注**（§4.4）。
4. **不动任何工具**（§4.5）。
5. **不动 `get_attraction_detail`**：那是读方案的那个工具，规则 11 第一条已经为它改过一次。
6. **不做「让模型自查事实真伪」**（§三 末）。

---

## 七、遗留

- **「本地库有这条，模型却自己答了」这种情况不验。** 库里躺着「广州塔」的资料，
  按本文规则，问「有什么看点」模型会自己答、不去查。理论上更好（答得更全），
  但**它和库里的说法可能不一致**。本版不管，先看实际跑出来会不会打架。
- **边界不是非黑即白。**「广州塔好玩吗」是主观题，归常识型，但模型可能顺口带出
  「门票不贵」——那归 §4.2 管，不靠判据 3 逐句兜。
- **`ASK_LIVE_HOURS.md` 仍未实现**（§二）。两篇都改规则 11，做的时候要注意先后，
  别让后做的那篇把先做的措辞覆盖掉。
