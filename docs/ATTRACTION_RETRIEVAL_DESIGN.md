## 一、一句话口径

**能用确定条件筛的，绝不交给向量。**

用户问"杭州下雨天去哪"——"下雨天"不是相似度问题，是**筛选条件**。
答案早就写在数据里（`tags` 含「室内」），直接筛；筛完的池子才交给向量排序。

分工是四步，各管一段：

```
词表   →  划定范围：只有这些词可选，不许自创
LLM    →  在范围内选：读懂用户意图 + 常识，挑出该筛的词
Chroma →  按选中的词筛（硬的、确定的）
向量   →  在筛完的池子里排相似度（软的、模糊的）
```

---

## 二、背景：为什么必须有"筛"这一层

### 2.1 纯向量的失败（实测）

不筛，只按 `city == 杭州` 过滤后直接算相似度，问「杭州下雨天去哪」：

```
0.6484  杭州灵山景区      tags=['避暑','亲子']     ← 溶洞
0.6410  杭州动物园        tags=['公园','亲子']     ← 露天
0.6237  杭州西湖风景名胜区-黄龙洞  tags=['避暑']    ← 溶洞
```

**浙江省博物馆没进前三**——而它的 `description` 里明写着「不受天气影响，适合雨天」。

**根因**：向量算的是"像不像"，用户要的是"能不能"。
"下雨天"与"避暑/溶洞"在语义空间里高度邻近（都指向"晒不着、凉快"），所以户外溶洞被顶上来了。

**危险之处**：向量检索**永远返回 top-k，永远是结果**。上面这三条看着都挺合理，
**错了也不告警**——用户从输出上看不出自己没拿到想要的。

### 2.2 加上"筛"之后（实测）

同样的问题，加一层 `tags 含「室内」`：

```
0.6169  浙江省博物馆(孤山馆区)  tags=['室内','博物馆','免费','亲子']   ✅
0.6120  浙江美术馆              tags=['室内','博物馆','免费','拍照']   ✅
0.5961  浙江图书馆              tags=['室内','免费','避暑']            ✅
```

池子从 34 条缩到 **6 条**，三条全是室内的。

**判据：这一层不是"更准一点"，是"从错变对"。**

## 四、数据契约（写进 Chroma 的规则）

向量库里的每条记录是**三样东西**（Chroma 的 `add()` 正是三个参数）：

```
① embeddings   page_content 算出来的向量
② documents    page_content 原文（命中后要给人看 / 给 LLM 读）
③ metadatas    全部结构化字段
```

### 4.1 进向量的文本 `page_content`

```
name + aliases + tags + description      用 | 分隔
```

- **`aliases` 为空数组时留空串**，所以会出现 `浙江省博物馆(孤山馆区)||室内|…` 这样的双竖线，**这是对的**
- **不加「景点名称：」这类标签词**——标签词在每条里都出现，会拉平所有向量之间的距离

### 4.2 metadata 的存储规则（**踩过坑，必须遵守**）

Chroma 的 metadata **只收标量**：`str` / `int` / `float` / `bool` 及数组。
**嵌套对象和 `null` 会直接报错。**

本单字段逐个核过，**两处必须转换**：

| 字段 | 现状 | 处理 |
| --- | --- | --- |
| `location` | `{"lng":120.14,"lat":30.25}` 嵌套对象 | 拍平成 `location_lng` / `location_lat` |
| `hours` | 10 条是 `null` | 换空串 `""` |
| `tags` | `["室内","博物馆",…]`，非空 | **原样存数组**（见 4.3） |
| `aliases` / `closed_days` | **可能是空数组 `[]`** | **空数组换成空串**——Chroma 拒收空数组，实测报 `Expected metadata list value for key 'aliases' to be non-empty` |
| 其余 11 个字段 | 已是标量 | 原样 |

### 4.3 `tags` 必须存数组，不能拼成字符串

**这是筛选能不能用的前提。**

```python
"tags": ["室内", "博物馆", "免费", "亲子"]     # ✅ 能筛
"tags": "室内,博物馆,免费,亲子"                 # ❌ 筛不了
```

**实测的过滤算子**（Chroma 1.5.9）：

| 写法 | 结果 |
| --- | --- |
| `{"tags": {"$contains": "室内"}}` | ✅ 命中 |
| `{"tags": {"$in": ["室内"]}}` | ❌ 命中空 |

**用 `$contains`，不要用 `$in`。**

多个条件用 `$and`：

```python
where={"$and": [
    {"city": "杭州"},
    {"tags": {"$contains": "室内"}},
]}
```

## 五、词表口径（本单**新增一条判据**）

### 5.1 词表是给 LLM 的候选清单，不是给程序查的字典

它存在的意义是**限制 LLM 不能自创词**。
没有这层约束，迟早会同时收到「雨天」「下雨天」「适合雨天」「雨天适合」四种说法，筛选就废了。

### 5.2 空词检查（**实测发现的问题**）

`data/tags.json` 列了 14 个词，逐个核对**实际被多少条记录使用**：

```
[场景]
   雨天      0 条   ← 空词
   夜游      9 条
   亲子      8 条
   避暑     10 条
   拍照     24 条
[属性]
   室内      6 条
   免费     19 条
   需预约     1 条
   无障碍     0 条   ← 空词
[类型]
   博物馆     5 条
   公园      4 条
   古镇      3 条
   山        0 条   ← 空词
   湖        0 条   ← 空词
```

越界检查**通过**：34 条记录里**没有一条**用了词表外的词 ✅

### 5.3 空词为什么是陷阱

```
用户问："杭州下雨天去哪"
   ↓
LLM 翻词表，看到「雨天」—— 这不明摆着正合适吗？
   ↓
挑中「雨天」
   ↓
筛出 0 条    ❌ 用户拿到空结果，且不知道为什么
```

**LLM 不知道哪个词有人用。** 空词给了它一个"看起来对、实则无效"的选项。

### 5.4 新增判据

> **词表里的每个词，至少要被 1 条记录使用。**

```python
for 词 in 词表:
    assert 用它的记录数 >= 1, f"{词} 没人用"
```

现在 4 个词是空的（雨天 / 无障碍 / 山 / 湖）。**要么删词，要么补记录，不能留着不管。**

**倾向：删词。** 理由——"下雨天能去"在现有数据里已经由「室内」表达了，
再加一个「雨天」是**同一个意思两个词**，这恰恰是受控词表要避免的。

（`无障碍` / `山` / `湖` 三个词是另一个情况：它们**本身是有意义的检索维度**，
不是「室内」那种语义重复。这三个更该**补记录**而不是删。
详见第十节待拍板。）

## 六、三条路径（LLM 怎么选）

| 用户问法 | 有明确条件吗 | 走哪条 | 做法 |
| --- | --- | --- | --- |
| 杭州下雨天去哪 | 有 → 「室内」 | **先筛后检索** | `where` 卡 tag，再算相似度 |
| 杭州免费景点 | 有 → 「免费」 | **先筛后检索** | 同上 |
| 灵隐寺要门票吗 | 有 → 景点名 | **查表** | 名字精确/包含匹配，取 `ticket_price` |
| 杭州有什么好玩的 | 没有 | **纯向量** | 直接算相似度 |

**原则：能确定的就别交给向量。**

## 七、提示词护栏（给 LLM 的）

1. **只能从词表里挑词，不许自创。** 挑不出就**不加筛选条件**，走纯向量。
2. **不许硬凑。** 用户问"有什么好玩的"，没有对应 tag 就是没有——不能随便挑一个充数。
3. **筛和查是两回事。** 问"要门票吗"是**查表**（名字匹配），不是筛选，也不是向量。
4. **查表 miss 必须"响"。** 名字对不上就是 miss，回落估算并标「估算」，
   不许拿一个相近的景点糊弄过去。

## 九、红线

- **不许把数字字段（`ticket_price` / `hours` / `duration_min`）拿去算向量。**
  它们在语义空间里几乎没有区分度——`0` 和 `30` 长得一样，算了也白算。
- **不许用 `$in` 筛数组 tags**，实测命中空。用 `$contains`。
- **不许把 `tags` 拼成字符串存。** 拼了就筛不了。
- **不许拿空词去筛。** 词表里出现空词 = 定向制造空结果。
- **不许改 `data/attractions.json` 的内容**来迁就检索（除了给记录**补 tag**，
  且补的 tag 必须在词表内）。价格、时间这些字段一个字都不许动。
- **不许拿相似度去否决筛条件。** 带了 tag 就是"筛"在答，向量只排序（10.5 节，实测踩过）。
- **不许把本地库的票价说成「估算」。** 它是 KB 查证的（`0`=确定免费，`null`=未知），
  和方案里那套"按类别估算"不是一个来源（12.4 节）。
- 接入 `AskAgent` 只**新增**工具与提示词条目，**不改**现有六个工具的行为与签名。

没有 tag 可筛（「山」删了）、词表里没有词能表达"库里没有山"、向量又会自信地返回溶洞。
这条的解法是补数据，不是调参数。

### 10.4 阈值实测：它只能做一半（2026-10-11 补）

第十节第 2 条拍板时，`min_score` 填的是 0.4，**没量过**。接入前补量了 20 条问句、100 个分数：

| 类别 | 例 | top1 分数区间 |
| --- | --- | --- |
| 相关 | 下雨天去哪、免费景点、适合带孩子 | 0.613 – 0.720 |
| **擦边**（旅游域内、库里没有） | 爬山、泡温泉、看海、游乐园 | **0.580 – 0.655** |
| 域外 | 修手机、考驾照、海底捞门店 | 0.467 – 0.537 |

**结论一：域外和域内是干净分开的。** 100 个分数里，域外最高 0.537，域内最低 0.554，中间一条空带。
取中点 → **`DEFAULT_MIN_SCORE = 0.545`**（原 0.4 太低，海底捞 0.421、地铁 0.451 全放行）。

**结论二（更重要）：擦边和相关的分数完全重叠，阈值挡不住擦边。**

```
0.6546  杭州有什么湖        ← 库里没有
0.6484  杭州下雨天去哪      ← 必须答对
0.6450  杭州哪里能爬山      ← 库里没有
0.6133  杭州有哪些博物馆    ← 必须答对
```

任何能筛掉「爬山」的阈值，会把「下雨天」「博物馆」一起筛掉——**那正是最需要它答对的两个**。
所以第十节第 2 条"设阈值就能不硬凑 top-k"**只实现了一半**：它挡得住"问错领域"，
挡不住"问对领域但库里没有"。后者靠两条兜：词表护栏（第七节）+ 提示词里那条"要自己核对类别"。

### 10.5 阈值只管纯向量那条路（2026-10-11 补，实测踩到的）

**这一条是接进 `AskAgent` 时跑真索引才暴露的。**

```
筛「需预约」→ 命中灵隐寺（全库唯一一条带这个 tag 的）
             → 但它对「杭州有什么要预约的」的相似度只有 0.5399
             → 被 0.545 丢掉
             → 用户拿到"没有命中的景点"——而库里明明有，还是唯一一条
```

**错在哪：** 带了 tag 就是**筛**在答，向量只负责把这批筛出来的排个序。
拿相似度把筛出来的东西丢掉，等于把"先筛后检索"的意义整个抹掉——
而这正是本单第一节那句口径的立足点。

**改法：** `apply_threshold = not tags`。阈值只在纯向量那条路上生效。

判据（`tests/test_retrieval.py`）：筛「需预约」要返回灵隐寺，**且**它那条的分数要低于阈值
（低了才说明这条判据真的在守东西）；另外把 `min_score` 拉到 0.99，带筛条件时也不许清空结果。

### 11.1 依赖方向翻了一次，得知道

`scripts/kb/kb_schema.py` 原文写着"**不 import travel_assistant 的任何东西**"，
理由是"这张表是运行时链路之外的一次性产物"。

**接入之后这句话不成立了**：`tags.json` 成了运行时输入（提示词要拿它约束模型）。
所以路径的所有者搬到了 `travel_assistant/kb/paths.py`，`kb_schema` 反过来 import 它。

两件事没变：`attractions.json` 仍是纯离线；`kb_schema` 那条"不启动服务就能单独跑"的性质仍在——
`travel_assistant.kb.paths` 只有 pathlib，不引 chromadb、不引 torch（`test_kb_runtime.py` 钉着）。

**为什么共用常量归运行时所有**：集合名、索引路径、编码器放在运行时，
离线脚本反过来引，这样"建的时候写进哪个集合"与"查的时候读哪个集合"**不可能对不上**。
放在离线那边就反过来了，是同一个道理但方向更别扭。

### 11.2 服务多背了什么（实测）

| 状态 | 常驻内存 | 启动 |
| --- | --- | --- |
| 服务装配完（本单之前） | 0.100 GB | 0.6s |
| + chroma | 0.135 GB | +0.3s |
| **+ BGE-M3（含 torch）** | **0.871 GB** | **+5.9s** |

`travel_assistant/` 在本单之前对 torch / sentence-transformers / chromadb 的引用数是 **0**。

**拍板：懒加载 + 进程内缓存。** 追问里有相当一部分根本不碰检索（问方案里写了什么、
判要不要改方案），不该为它们把服务启动拖长 5.9s、健康检查窗口跟着变。
代价是第一个问这类问题的用户多等一次加载。

**实测确认懒加载生效**：`build_ask_tools()` 跑完常驻仍是 0.100 GB，第一次真的检索时才涨到 0.976 GB。

### 11.3 索引是 gitignore 的产物 → 部署要先建

`data/chroma/` 不入库（第十节第 3 条）。所以**部署时必须先跑一次建索引**，否则线上是"没建"。
工具层接住了这个情况：`IndexNotBuilt` 会被翻成一句"本地景点资料库还没建好，这次查不了"，
模型照实转告，不会把栈打给用户看。

**多副本要注意**：Chroma 是嵌入式库，每个副本各有一份自己的索引文件。N 个副本 = N 份索引 + N 份 0.87G 模型。

## 十二、接进 `AskAgent`（2026-10-11 已做）

检索层对外的调用面没变：

```python
search_attractions(city, tags=None, query=None, top_k=3) -> list[dict]
```

- `tags=None` → 纯向量
- `tags=["室内"]` → 先筛后检索
- 返回的每条带**全部字段**（metadata 里都有，不用回表）

### 12.1 工具怎么摆的

新增第 7 个工具 **`search_attractions_by_tag(tags)`**。三个决定：

**一、名字不叫 `search_attractions`，因为那个名字已经被占了。**
`ask_tools.py` 里原本就有一个 `search_attractions`——零参数、**联网**、按原始请求的城市+偏好
去高德捞候选。两个东西数据源完全不同，撞名模型就没法选。判据钉着这一条。

**二、它是有意破"零参数"这条约定的。**
`ask_tools.py` 开头写着联网那三个零参数，因为"这几个值让模型自己填就会被编造"。
但**"筛哪个词"正是要模型做的判断**，从上下文取不出来。
所以只让它填 `tags`，**城市仍从 `context.request.city` 取**，不让模型填。
护栏不是参数来源，是**词表**。

**三、词表写进工具说明，而且是现读的。**
`describe_vocabulary()` 每次建工具时现读 `data/tags.json`，不抄一份常量——
抄了就会在改词表时变成一句过期的话。

**踩到的坑**：f-string **当不了 docstring**。CPython 只把常量字符串存进 `__doc__`，
JoinedStr 不行，`f"..."` 当第一条语句会让 `__doc__` 是 `None`。所以走 `@tool(description=...)`。

### 12.2 工具的两处护栏

| 情况 | 返回 |
| --- | --- |
| 城市不在库里（库里只有杭州，问广州） | 照实说"目前只有杭州，没有广州的景点"，**不许**把杭州的当广州的答出去 |
| `tags` 里有词表外的词（模型自创，或挑到已删的空词「山」） | 当面拒绝并列出可选词——而不是筛出 0 条让模型以为"库里没有" |
| 索引没建 | "还没建好，这次查不了"，让模型改用方案内数据 |
| 筛出来 0 条 | "没有命中的景点"，不是空串 |

**为什么要单独拒词表外的词**：筛 0 条和"这个词根本不该用"是两回事，
后者要让模型知道是自己挑错了，前者是库里确实没有。

### 12.3 提示词加的两条（`ask_agent.py` 第 11、12 条）

- **第 11 条**：分清楚 `get_attraction_detail`（问方案里已有的那个景点）和
  `search_attractions_by_tag`（问有什么符合条件的）。词表在工具说明里，不重复抄。
- **第 12 条**：**本地库的答案要自己核对类别。** 检索永远会返回几条，返回了不等于对得上——
  用户问爬山却返回溶洞、问湖却返回博物馆，就要说库里没有。
  **这条优先于"尽量给出答案"。**

第 12 条是 10.4 那个结论的落点：阈值挡不住擦边，向量会给一个自信的错误答案，
最后一层防线是模型自己看一眼"返回的东西到底对不对得上"。

### 12.4 门票口径别混

**本地库的门票和方案里那套不是一回事，渲染时刻意分开了：**

| 来源 | 口径 |
| --- | --- |
| 本地库（`attractions.json`） | KB 自己查证的：`0` = 确定免费，`null` = 未知 |
| 方案（`get_attraction_detail`） | "按类别估算"（高德没有此字段） |

所以本地库那条**不写「估算」**，写了反而是错的。
（`ask_agent.py` 第 5 条要求"标了估算的必须保留估算二字"——那是针对方案那套的。）
