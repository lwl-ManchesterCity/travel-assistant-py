# 景点外部资料库建设（离线建表 · 供追问与规划取数）

> 对象：执行建表的 agent
> 前置：无。本单**不改动任何现有代码**，只产出一份数据文件 + 一个离线脚本
> 范围：**只做「建表」**——把景点资料采集并写入 `attractions.json`。检索接入（查表 / 向量）是下一轮，本单预留接口即可
> 依据：与项目主的讨论结论（2026-10-10），被否掉的方案见第三节

---

## 一、一句话口径

建一张**离线的景点资料表**，补上高德**确定拿不到**的那几格（门票、开放时间、闭馆日），
外加一份可检索的简介与场景标签。**运行时只查表，不联网。**

---

## 二、背景：为什么是「表」，不是「通用 RAG」

### 2.1 高德的能力边界（有实测出处）

`MIGRATION_NOTES.md` §6.5 记录：高德 POI 接口**顶层 47 个字段没有价格字段**，
`biz_ext.cost` 为空、`ticket_ordering` 恒为 `'0'`/null；酒店侧实测 10 家 `biz_ext.cost` 也全为空。

| 追问会问到的东西 | 高德 | 现状 |
| --- | --- | --- |
| 景点在不在、在哪、坐标、电话、附近有什么 | ✅ | 高德，权威 |
| 城际怎么走、多少钱 | ✅ | 高德 `transit/integrated` |
| **门票多少钱** | ❌ 实测无此字段 | 按类别猜：自然风景 60、人文历史 50…共四个值（`amap_attraction.py:228`） |
| **几点开门、周几闭馆** | ❌ | 没有 |
| **要不要预约、排队多久** | ❌ | 没有 |
| 这个景点适合上午还是傍晚 | ❌ | 按名字里的类别词猜（山/公园→上午，塔/夜景→傍晚） |

**最能说明缺口的一处**：`static/index.html:356` 追问框的 placeholder 写的就是
「例如：第二天为什么这么赶？**西溪湿地要门票吗？**预算还剩多少？」
而系统提示词第 4 条是「工具没给到的信息，直接说没查到」——**自己邀请用户问的问题，agent 只能回「没查到」。**

### 2.2 判定规则：问题有没有唯一正确答案

| 问题 | 有唯一答案吗 | 用什么 |
| --- | --- | --- |
| 西溪湿地门票多少 / 几点关门 | ✅ 有 | **精确查表** |
| 这个景点有什么看点 | ✅ 有（简介就是那一行） | **精确查表** |
| 杭州下雨天去哪 / 适合带小孩的室内景点 | ❌ 没有，只有「哪些相关」 | **向量检索** |

**结论：数字和简介都走查表；只有「没指定景点」的开放问题才需要向量。**
一份数据两种用法——`ticket` / `hours` 走精确匹配，同一行的 `description` 同时进向量索引。
**不建两个库。**

### 2.3 本单范围

**只做建表。** 检索（查表函数 / 向量库）下一轮，本单把数据文件做出来、schema 定下来即可。

## 三、被否掉的四条路（防止回头走）

1. **通用 RAG 直接塞官方简介。** 官方简介里**没有用户会用的词**——浙江省博物馆的简介写「位于杭州市西湖区，馆藏文物十万余件」，
   用户问的是「杭州下雨天去哪」，「下雨天」这个词在语料里根本不存在，向量距离很远，**召回必然失败**。
   这是 RAG 最常见的死法：**不是向量库不行，是语料的口吻跟提问的口吻对不上。**
2. **爬网页。** 能稳定爬到的（名称、坐标、类型）**高德已经给了**；高德不给的那三格（门票、开放时间）
   恰恰**没有好的公开源可爬**。爬虫能补的部分与已有部分高度重叠，外加授权与长期维护成本。
3. **运行时联网查。** 每次追问多几秒、有成本、结果不可复现。**联网只在建表那一刻用。**
4. **`ticket_price` 缺失时填 0。** 会让系统把「不知道」当成「免费」——预算里门票那一桶直接少算一笔，
   而且**不报错、不告警**。必须区分 `0`（确定免费）与 `null`（未知）。详见第七节。

## 四、数据模型

### 4.1 单条记录 schema

```json
{
  "id": "hz-zj-museum",
  "amap_poi_id": "B023B0AB5H",
  "name": "浙江省博物馆",
  "aliases": ["浙博", "浙江省博物馆之江馆"],
  "city": "杭州",
  "location": { "lng": 120.1551, "lat": 30.2741 },

  "tags": ["室内", "免费", "亲子", "雨天", "博物馆"],
  "category": "人文历史",

  "ticket_price": 0,
  "hours": "09:00-17:00",
  "closed_days": ["周一"],
  "duration_min": 120,

  "description": "位于西湖边，全程室内参观，不受天气影响，适合雨天或带孩子慢慢逛。",

  "source_url": "https://www.zhejiangmuseum.com/...",
  "updated_at": "2026-10-10"
}
```

**字段说明（都是约束，不是建议）：**

| 字段 | 类型 | 约束 |
| --- | --- | --- |
| `id` | str | 稳定主键，自造（`城市拼音-短名`）。**不许用 `name` 当主键** |
| `amap_poi_id` | str | 高德 POI 响应的 `id`，**与高德对齐的外键**，比名字可靠 |
| `aliases` | list[str] | 用户可能说的别称。本项目已踩过坑：用户说「白云山」，高德返回「白云山风景名胜区」 |
| `tags` | list[str] | **只能取自词表**（4.3），校验不通过即失败 |
| `category` | str | **必须对齐现有 `Attraction.category`**：自然风景 / 人文历史 / 美食购物 / 城市漫游。现有打分与门票估算全依赖它 |
| `ticket_price` | int \| **null** | `0` = 确定免费；**`null` = 未知**（回落估算并标「估算」）。**禁止用 0 表示未知** |
| `hours` | str \| null | 先当字符串存，**不做结构化**（不分旺季淡季、不分时段） |
| `closed_days` | list[str] | 如 `["周一"]`；不确定填 `[]` 而不是编 |
| `duration_min` | int \| null | 建议游览时长 |
| `description` | str | 一段自然语言，**同时用于向量化**。控制在 200 字以内 |
| `source_url` | str | **必填，不许为空**。模型读的那个页面 |
| `updated_at` | str | `YYYY-MM-DD` |

### 4.2 字段来源分三层

| 层 | 字段 | 怎么来 |
| --- | --- | --- |
| **一：高德直接给** | `amap_poi_id` / `name` / `city` / `location` / `type` | 批量拉一次 |
| **二：能推导** | `category`（由 `type` 映射）、部分 `tags`（type 含「博物馆/展览馆/美术馆/图书馆」→ `室内`）、`duration_min`（按 category 给默认值） | **写死映射表，不用人看** |
| **三：只能联网 + LLM** | `ticket_price` / `hours` / `closed_days` / `description` / 场景类 `tags`（亲子、雨天、夜游） | 见第五节 |

### 4.3 受控词表 `tags.json`

**`tags` 不允许自由文本**——否则会出现「雨天 / 适合雨天 / 下雨天 / 雨天适合」四种写法，**检索立刻崩**。

```json
{
  "场景": ["雨天", "夜游", "亲子", "避暑", "拍照"],
  "属性": ["室内", "免费", "需预约", "无障碍"],
  "类型": ["博物馆", "公园", "古镇", "山", "湖"]
}
```

景点记录里的 `tags` 必须是这三个数组的并集的子集。改动词表要单独提交。


- **有** → 第三层少一格，`hours` 走接口
- **没有** → `hours` 也归 LLM 联网

**结论写进本文件末尾的「实施记录」。** 不要跳过这步就开写脚本。

### 第 1 步：拉骨架

挑**一个城市的核心景点 30 个**（建议杭州，`knowledge_base.py` 里已有 4 个可对照）。
真跑 `/v3/place/text`，**把原始响应存成 fixture**（不是归一化后的对象）。

> 注意：`scripts/fixtures/result-plan.json` 里存的是**归一化之后**的对象，没有 `biz_ext`，

从 fixture 生成 `amap_poi_id` / `name` / `city` / `location` / `category`，

### 第 3 步：联网补第三层

对每条调 LLM + 联网搜索，要求返回 `ticket_price` / `hours` / `closed_days` / `description` / 场景 `tags` / `source_url`。

**一条一条来，不要一次塞 30 条让模型批量输出**——批量必串味（把 A 的门票写到 B 上），
且这是**看不出来的静默错误**。

### 第 4 步：校验（见第七节，脚本必须实现）

### 第 5 步：抽检 5 条

**不是人工填表，是质检。** 花十分钟看 5 条对不对，据此判断错误率。
不做这步**无从知道错误率是 5% 还是 50%**，而它决定这张表能不能用。

## 六、提示词护栏（给建表时的 LLM 调用）

必须写进提示词，四条：

1. **必须返回你读的那个页面的 URL**（`source_url`）。**没有 URL 就不许填值。**
2. **不确定就填 `null`，不许猜。** 宁可留空也不要编一个看起来合理的数。
3. **`tags` 只能从给定词表里挑**，词表外的词一律不许出现。
4. **一次只处理一个景点。** 禁止合并输出多条。

第 2 条是关键：不做这条，你会得到 300 条看起来完整、实则一半是编的表，**而且看不出来**。

## 八、检索侧（**下一轮做，本单只留接口**）

数据文件做好后，检索按以下口径接——**本单不实现，但 schema 要能支撑**：

1. **一条记录 = 一个 chunk。** 不要用通用文本切分器。理由：硬切会把一个实体切成两半，
   更糟的是**跨实体串味**（第 30 条的尾巴和第 31 条的头落进同一个 chunk）。
   JSON 的数组边界就是天然的切分边界——这是结构化数据做 RAG 的最大优势。
2. **向量化的文本显式拼接**，写成一个函数：`name + aliases + tags + description`，用 `|` 分隔。
   **不要加「景点名称：」这类标签词**——标签词在每条 chunk 里都出现，会拉平所有向量之间的距离，降低区分度。
3. **metadata 带上全部结构化字段**：一个作用是命中后直接可用（不用回表），
   另一个是**先过滤后检索**——问「杭州下雨天去哪」时先用 `city == 杭州` 过滤，再算语义相似度。
   用确定的约束去过滤，别让向量去猜。
4. **查表侧的 miss 必须「响」**：名字对不上就是 miss，回落估算并标「估算」。
   向量检索的问题在于它**永远返回 top-k，永远有结果**，错了也不告警——所以数字字段不要走向量。

## 十一、实施记录（2026-10-10 执行完毕）

### 1. 第 0 步结论：**高德给开放时间，且比预期好**

实测杭州 20 个景点样本（`extensions=all`）：

| 字段 | 覆盖 | 内容质量 |
| --- | --- | --- |
| `biz_ext.opentime2` | **18/20 = 90%** | 同时含开放时段、**闭馆日**、最晚进入时间、节假日例外 |
| `biz_ext.open_time` | 11/20 | 简版时段，作`opentime2` 的备份 |
| `biz_ext.cost` | 1/20 | 唯一有值的那条是**餐饮店**（人均 68 元），对景点无效 |

**与本文件第五节的预设不同**：原文设想「`hours` 也可能归LLM 联网」。实测结论是
**`hours` 与 `closed_days` 都能从 `opentime2` 离线推导**，第三层只需联网补
`ticket_price` / `description` / 场景类`tags` / `source_url`，工作量少一格。

典型样本（可直接看出为什么能推导）：

```
周二至周日 09:00-17:00开放 最晚进入16:30； 周一 全天不开放(遇法定节假日正常开放…)
4月1日至10月31日 周二至周日 09:00-17:00开放（16:00停止入园）；周一 不开放(…)
```

**推导时踩到的四个坑**（都写进了 `normalize.parse_opentime2` 与对应测试）：

1. **全角破折号**：高德混用 `-`、`–`(U+2013)、`―`、`~`、`至` 五种分隔符。
   只认半角会让「周二–周日 09:00–17:00」整条解析失败——中国丝绸博物馆、良渚博物院都栽在这里。
2. **`00:00-24:00` 是占位不是答案**：实测 27/30 条是这个值。它是「全天开放」的占位，
   存进 `hours` 会让追问「几点关门」得到荒谬答案。已作为「未知」处理（`null`）。
3. **闭馆日与开放区间混在同一子句**：「周二至周日 09:00-17:00 周二 全天不开放」里，
   「周二至周日」是开放区间，只有最后那个「周二」是闭馆日。误判会让 `closed_days` 多出「周日」。
4. **闭馆关键词有六种写法**：不开放 / 闭馆 / 闭园 / 全天关闭 / 停止开放 / 休息。

### 2. 抽检 5 条：**5 / 5 关键字段正确**

| 景点 | 票价 | 时段 | 闭馆 | 出处 | 判定 |
| --- | --- | --- | --- | --- | --- |
| 河坊街景区 | 0（免费） | — | — | 携程攻略页 | ✅ |
| 云栖竹径 | 8元 | 07:00-17:00 | — | 杭州市园林文物局公示 | ✅ |
| 良渚博物院 | 0（免费） | 09:00-17:00 | 周一 | 博物院官网参观须知 | ✅ |
| 杭州灵山景区 | 57元 | 08:30-17:00 | — | 携程攻略页 | ✅ |
| 雷峰塔景区 | 40元 | 08:00-19:00 | — | 杭州市园林文物局公示 | ✅ |

票价、时段、闭馆日、`source_url` 全部与出处一致，**关键字段错误率 0%**。

**抽检发现的 1 处次要偏差**（不影响可用性，记此备查）：
`duration_min` 是第二层按 category 统一给的（雷峰塔被判成180 分钟），
实际上该塔参观约 1 小时。**`duration_min` 在 4.1 表里就是「建议值」不是「事实值」**，
后续接检索时应按 `name` 覆写高价值景点，或接受这个偏差。
