# 追问指定"某天必去某景点"设计（day_attraction_pins）

状态：**已实施（2026-10-09，task #44–#47）；2026-10-10 补全酒店那一格（task #50，129 passed）**。最终口径：
- **一次追问可点名多个必去景点**（`pinHints` 数组，前端两卡文案都按多个渲染）。
- **只点 1 个**：以它为中心补附近高分（靠"酒店锚到它 + 就近档"），它留作当天最后一站。
- **点 2 个及以上**：这天就=你点名的这些，**不再自动补别的**；游玩先后由 `PlannerAgent._order_day_pins` 算（2026-10-10 改，见下节"顺序判据"），不再让模型凭空猜。
- 酒店那一格**分两种情况，别混**（2026-10-10 修正）：
  - 那句话里的住宿位置**就是当天点名的某个景点**（＝确认卡上点了"把酒店挪过去"、后端代填的那格）→
    重挑离**当天最后一站**最近的一家，用的是**这一天的候选池**（含按位置补搜回来的那批），不是全城那份。
    名字对得上按互相包含判（代填写的是用户原话"白云山"，景点实体名可能是高德给的"白云山风景名胜区"，只比全等会让"挪"静默失效）。
  - 那句话里的住宿位置是**另一个地名**（"第二天必去白云山和广州塔，酒店离广州图书馆近点"）→ **不动酒店**，
    主链路按那个位置圈出来的结果就是最终结果，并在备注写一句"住宿位置仍按你点名的『X』，没有跟着挪到当天最后一站附近"。
    早先的版本不分这两种，一律按末站重挑，等于用户亲口说的位置被"顺路"覆盖。
- 只在有必去景点那天生效，**普通链路一行不动**；不填逐天与现状一字不变。
- 补搜：候选池按名字对上 → 对不上 `find_attraction_by_name` 按名补搜 → 还没有才记"未找到、未排入"；超预算/多绕以具体数字写进备注。

## 一、目的与一句话口径

让用户在**方案追问**里说"我希望第二天的景点有白云山"，重规划后第 2 天一定排进白云山。
口径（已定）：**客户说的算数 → 必去景点强制赢**，绕开预算、名额、距离这些常规约束；代价（超预算、多绕路）如实写进方案备注，不静默。唯一强制赢不了的情况：按名字在高德也搜不到这个 POI——没有实体可放，只能跳过并明说。

这是本项目第一次让**用户硬约束压过打分**（酒店锚点只是圈候选池、仍由打分挑；这里是"必须出现"）。

## 二、核心机制：必去景点 = 当天基准点

现有单天逻辑是"先算当天那批景点的中心 → 按中心+价格定酒店 → 再定具体景点"。
一旦这天有必去景点，**不再拿全城高分景点算中心**（否则 (0,0) 那堆和 (20,20) 的白云山一平均，酒店被拽到对谁都不挨着的中间）。改成：

- 这天先定一个**基准点集合**：
  - 要挪酒店 → 基准点 = 那几个必去景点；
  - 不挪酒店 → 基准点 = 必去景点 + 那个留在原处的酒店。
- 酒店（要挪时）和其余景点，都在基准点围出的范围里**越近越好**地挑。
- **扩圈**：先 0–10km，不够再 0–15km，再不够 0–20km（最小 0，贴着最好）。**不为凑数把 20km 外的硬塞进来**，否则又变回"孤零零一个在远处"。
- **多个必去景点离得远**（如 珠江(1,0) + 白云山(11,0)）：酒店取"到最远那个必去景点的距离尽量小"（min-max），自然落在两点连线之间（取 (5,0)/(3,2)/(7,1) 这类，不取 (-3,0)/(15,0) 超出两端、或 (0,4) 甩在旁边）。这天本就跨两头，通勤长写进备注。

## 三、"要不要挪酒店"——多弹一张确认卡（关键交互）

- 触发条件：追问判成**"指定必去景点"、且这句话没同时提酒店**时，才多弹一张确认卡：`要不要把酒店也挪到白云山附近？ [是 / 否]`。
- 这不是"来回对话的多轮"（那要等以后加登录做长期记忆），只是**同一次提交里前端多一步确认**，服务端全程无状态。
- 选**是** → 后端等于替用户把"期望住宿位置=白云山"填上（复用现成的酒店锚点链路：地名→坐标→周边补搜→圈池→min-max 定店），酒店贴必去景点。
- 选**否** → 不碰酒店，当天景点在"原酒店 ↔ 白云山"中间找。
- 若这句话本来就提了酒店（"第二天酒店离白云山近点"）→ **不弹**，直接按酒店锚点走（这条现在就已能做）。

优先级：**追加规划 > 第一轮填的住宿位置**。冲突时以这次追问为准。

## 五、非目标（这版不碰）

- 不做"删除/排除某景点"，只做"必去"（加法）。
- 不做"必去某餐厅 / 必住某一家酒店"。
- 不改酒店三项打分公式与既有常数；不新写一套选酒店逻辑（挪酒店复用酒店锚点）。
- 第一轮委托单**不加**"必去景点"输入框，纯靠追问。
- 不做真·多轮对话；"挪酒店吗"是同一次提交内的额外确认步。

## 七、判据（可机器核对）

1. 不填必去景点 → 逐天景点与现状完全一致（向后兼容）。
2. 第 2 天必去=白云山且已在池 → 结果第 2 天含白云山。
3. 白云山不在池 → 按名补搜命中后排进第 2 天。
4. 补搜也搜不到 → 出现"没找到…未排入"备注，不崩、不静默。
5. 必去景点票价超日预算 → 仍排入，备注写超出金额，不 drop。
6. 基准点=必去景点：其余景点按 0-10→0-15→0-20 扩圈挑，不选 >20km 的。
7. 两个必去景点 (1,0)+(11,0) → 酒店落在两点之间（min-max），不选超出两端或甩旁边的。
8. 挪酒店=是 → `day_hotel_anchors[day]` 被写成必去景点名、酒店贴它；=否 → 酒店不动、景点在"酒店↔必去景点"之间。
9. 同一景点被第 2 天必去、第 1 天也想选 → 第 2 天赢（全局预留）。
10. 追问"第二天要有白云山"摘出 `pinHint=白云山, pinDay=1`；"第二天酒店离白云山近"摘出 `anchorHint=白云山`、`pinHint` 空（不弹挪酒店卡）。
11. 第一轮填过住宿位置、第二轮追加与之冲突 → 以第二轮为准。

## 九、当天游玩先后的判据（2026-10-10 补全，取代早先"交给模型按天气/环境猜"）

**为什么改**：原来 `LlmNarrationService.order_attractions` 只拿到三行输入——当日天气、景点名加类别、要输出的名单，
**没有任何坐标、也没有收工地点**，提示词里那句"整体少折返"它根本没法执行；而且喂给它的名单顺序就是用户原话顺序，
于是"照抄我给的顺序"和"它真的判断过了"输出长得一样，系统分辨不了、也没有校验。实测就排出"先广州塔、后白云山"，
把广州塔↔白云山那段走了两遍。

**现在的规则（`PlannerAgent._order_day_pins`）**，收成一句：**有收工地点就按里程最短排；只有酒店要跟着末站走时，才让时段常识决定谁是末站。**

1. 收工地点三种来源：用户指定了住宿位置→那个位置；确认卡点了"把酒店挪过去"→还没定（`None`）；其余（含选"不挪"）→当晚那家已定的酒店。
2. 点名的站全排列（`itertools.permutations`），每条算 `Σ 相邻站直线里程 + 末站→收工地点`，按里程升序。
3. 比最省那条**多绕不超过 3 公里**的算并列；只有并列才交给模型（`choose_attraction_order`）在候选里挑，
   规则写死"默认取编号 1，只有把该上午爬的山排到了后面、把该傍晚看的塔排到了前面才允许换"，
   并禁止它自己估距离、禁止提出候选之外的顺序。
4. 模型不可用或输出不合规（没编号、编号越界）→ 代码按**时段常识表**在并列里挑错序最少的一条；表也判不出（全是"都行"）→ 取最省路那条。
5. 常识表写死在 `planner_agent`：名字含"山/森林/公园/湖/瀑布/海滩/湿地/峡谷/岛"＝上午更合适，
   含"塔/摩天轮/观景/夜景/观光/灯光/游船"＝傍晚更合适，其余＝白天都行。**只认类别词，认不出就说都行，不编造具体景点的开放时间。**
6. 依据写进备注（"先后按少绕路排，全程约 29 公里"／"先后按上午爬山、傍晚看夜景这类常识排…"），不静默。

**为什么"不联网"也成立**：没有联网就没有"查不到"这个分支，判定完全可复现；代价是它只认类别不认具体景点
（不会知道某座塔周一闭馆）。要针对具体景点拿资料，属于后面接外部检索那一档，届时只是把第 3、4 步的依据换源，链条不动。
